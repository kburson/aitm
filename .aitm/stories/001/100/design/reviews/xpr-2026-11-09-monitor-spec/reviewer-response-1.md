## Findings

1. **The interval-time basis is undefined for observations without a native start boundary, which affects Grok directly (Reports and compatibility, line 59).** The report puts an observation in an interval by "the observation's first verified native start boundary" and marks "an unknown observation time as a coverage gap outside the requested interval totals." The spec makes the Grok observation "a verified completion" (line 47). The #101 evidence establishes a durable `turn_completed` record and a snapshot "completion time." It does not establish a durable native turn-start timestamp. The only start-side signal is the prompt-scoped `UserPromptSubmit` hook, which matched just 30 of 41 sampled completions, and the spec itself says hooks "can be absent, disabled or missed" (line 37). As written, a qualified Grok turn without a retained prompt hook could fall outside every interval total. That is an admitted charge missing from the interval report, even though line 47 lets "a complete qualified native completion" count. Codex `token_count` rows and Claude streamed rows also carry per-row times, and the spec does not say which of those is the "start boundary" for a whole request. The adapter interface (line 43) declares boundaries, token categories and pricing evidence, but no time basis. *Failure scenario:* during Grok qualification (line 79), a hook-disabled or missed-hook turn is counted in the project total for "all time" but missing from every bounded interval. The reconciliation check between the summary and interval reports then fails, or the builder invents a fallback.

2. **Precedence is undefined when a verified scope marker contradicts a registered anchor of another project (lines 17 and 21).** The spec covers an outside reviewer whose checkout is *not* registered ("admitted through a verified scope marker without turning that reviewer's whole checkout into a project anchor"). It also says a verified marker "can establish the project where checkout evidence is absent" and that "an ordinary marker cannot silently override a contradictory project anchor." It does not say what happens when the reviewer's session runs in a checkout registered to project B and carries a verified marker for project A. That is the normal cross-project review case: an `ai-peer-review` maintainer's session reviewing an AITM artifact, or the reverse. Three readings are plausible: the verified marker wins, a dedicated handoff is required (line 23), or a conflict is raised. They produce different totals. The verification section exercises "an unmarked review" and "an ambiguous project claim" (line 75), but not this case. *Failure scenario:* two builders implement different precedence rules. One charges the review to B, the reviewer's checkout. The other charges it to A, the reviewed project. Both pass the listed verification.

3. **The spec does not say how unsupported host surfaces are handled when they share an approved root (lines 11, 17 and 45).** Initial coverage is "Codex Desktop on macOS" and "the supported local Codex CLI surface" on Linux. Codex CLI on macOS is not listed, yet it normally writes rollouts under the same user Codex root that the Desktop adapter watches. Shared roots are "watched once" per provider installation (line 17). The spec does not say whether rollouts from an unqualified surface or version in an approved root are excluded with a coverage reason, held, or admitted under the Desktop adapter's semantics. #83 requires unsupported versions to yield explicit coverage gaps. The multi-surface, shared-root case is new in #100 and should state the same rule at the surface level, keyed by the recorded client surface and version. *Failure scenario:* a developer runs `codex` CLI on the Mac in a registered checkout. The Desktop adapter either silently counts usage whose counter semantics were never qualified for that surface, or silently drops it with no visible coverage gap.

4. **The verification section has no privacy or allowlist check for the new decoder, routing state and exports (lines 17 and 73–79).** Line 17 states strong rules: no prompts, responses, tool arguments, credentials or raw provider IDs in persisted collector data and reports, and no raw paths in exports. #83's readiness checks included "show no duplicate observations or private content" with a fixed field allowlist. #100 adds a new Grok decoder whose source files hold prompt, response, tool and hook-output payloads next to usage (#101 consequence 3). It also adds hook wake notifications, routing holds, a service journal, a recovery log and per-project exports. None of the five verification bullets checks that these new stores and exports omit private content. None checks that one project's export or pseudonyms do not leak another project's identities. *Failure scenario:* the Grok decoder or the wake inbox persists a raw session ID or transcript path, or a project export includes a sibling project's display name or routing reason. Every listed verification case still passes.

## Required changes

1. For Finding 1, require each adapter to declare its observation time basis in the versioned contract (line 43). For example, the native start boundary where one is proven, otherwise the verified native completion time, with the basis recorded on the observation. Use that declared basis for interval membership (line 59). Reserve "unknown observation time" for observations with no verified native time at all. State the Grok basis explicitly in the Grok bullet (line 47).
2. For Finding 2, state the rule for a verified scope marker that contradicts a registered checkout anchor of another project. Either require the dedicated handoff path of line 23, naming the current anchor project, or define the verified marker's precedence and its conflict behavior. Add this case to the first verification bullet (line 75).
3. For Finding 3, state that an adapter admits only the host surfaces and versions it declares as qualified. Sources in an approved shared root from any other surface or version get an explicit, sanitized coverage reason and are excluded from totals. Name macOS Codex CLI's status in the scope paragraph (line 11).
4. For Finding 4, add a verification item. It should scan the persisted service journal, holds, wake notifications, recovery log, per-project ledgers, reports and every export for prompt, response, tool-argument, credential, raw provider-ID and raw-path content against a fixed field allowlist, including Grok sources. It should also verify that no project export contains another project's identities, pseudonyms or routing reasons.

## Optional suggestions

1. **Grok project-ownership basis.** "Use provider-recorded checkout or explicit enrollment" (line 17) assumes the provider records a checkout. #101 shows prompt lineage, not a recorded Grok working directory. If no hook receipt exists and Grok records no checkout, the turn cannot establish a project and is held. Consider stating which Grok evidence establishes project ownership, separately from story attribution, so qualification tests it directly.
2. **Wake-notification retention.** Hook notifications (line 29) may contain raw session IDs or transcript paths. Consider stating that they are consumed and removed, or keyed, once reconciled, so they are not retained private state that conflicts with line 17.
3. **Define "overlapping" anchors (line 15).** State whether nesting counts as overlap or only identical paths do. For example, a separately registered project cloned inside another project's checkout, or an external worktree directory. If nesting is rejected, say so, because it blocks some common layouts. If it is allowed, state the resolution rule, such as the deepest anchor.
4. **Handoff sentence clarity (line 23).** "the native receipt at the first supported request or turn after the receipt in that stream" is circular. Consider: "the native receipt of the handoff command, which takes effect at the first supported request or turn boundary after that receipt in the same stream."
5. **Explicit park source (line 34).** "Explicit park" has no defined issuer. Consider naming it, for example an operator or workflow park command, and stating that it carries no scope authority, as line 37 already says for idle demotion.
6. **Grok hook trust in production.** The spike allowed probe hooks with a process-scoped folder-trust override. Production capture through prompt hooks implies a persistent, owner-approved trust grant in each registered Grok checkout. Consider listing that in the Grok qualification path, or deferring it to the plan explicitly.

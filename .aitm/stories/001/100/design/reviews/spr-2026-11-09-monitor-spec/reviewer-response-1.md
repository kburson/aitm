## Verdict — REVISIONS REQUIRED

I reviewed all 80 lines of the #100 specification and both complete spike reports. The specification accurately treats #101 as evidence for a candidate Grok whole-turn carrier on one macOS build and #102 as evidence for Linux primitives and provider interfaces. Production admission and live platform qualification remain open.

## Required findings

1. **Define when a handoff takes effect and how it ends if proof fails.** Spec lines 21–23, 39, 74. A delayed receipt, competing handoff, or missing proof can leave the affected requests and their eventual disposition unclear. Define which native boundary a proposal can bind, how duplicate or superseded proposals are rejected, and when held requests return to the proven scope or become a coverage gap. Cover A→B→C when the provider keeps reporting checkout A. The spec should say whether a verified second handoff suffices or the operator must rebind the session.

2. **Apply registration changes to evidence at the time of the request.** Spec lines 15–17, 39, 65. The initial enrollment rule leaves disablement, removal, and re-enrollment underspecified. Define how a registration change applies to an in-flight request, delayed revisions to eligible usage, and activity generated while a project or source was disabled. Add a disable-and-re-enable case that verifies the disabled interval stays excluded even when its files are discovered later.

3. **Define how existing usage enters the first published monitor view.** Spec lines 51–53, 59, 63–67, 76. The new read path requires a journal ACK, while pre-cutover ledger entries have no such ACK. Specify how the verified legacy ledger sequence becomes visible in current reports and exports without manufacturing service-wide claims from project-keyed references. Verify both first-report parity for the migrated interval and that rediscovered legacy evidence cannot be charged to another project.

4. **Specify recovery from an older coordinated backup.** Spec lines 53, 59, 67, 76. A matching journal and ledger backup can still predate a handoff, a published route, or a Core acceptance. Define what attribution and publication evidence must be recovered before routing resumes. When that evidence is unavailable, specify which spans are held and how the report exposes the gap. Test a restore that predates both a scope change and an accepted export.

5. **Resolve queue saturation across projects.** Spec lines 37–39, 53, 74–76. An unavailable project can fill the pending queue or pin the cursor of a stream that later switches to a healthy project. Define the progress guarantee for healthy projects on independent streams, and what users see when a shared stream must pause. Verify both cases with a full queue and confirm replay after the blocked ledger recovers.

6. **Prevent delayed revisions from rolling back published usage.** Spec lines 29, 43, 51–53, 59, 74. An idempotent write prevents duplicate delivery of the same revision. It can still accept an older revision after a newer one. Define when native evidence establishes supersession, when incomparable revisions create a conflict, and how both the ledger write and ACK preserve the published revision. Test a stale revision arriving after a newer revision has been acknowledged, including across restart.

7. **Make interval and pricing results reproducible across summary and drilldown.** Spec lines 43, 47, 57–59. Specify which native time governs requests and indivisible spans that cross an interval boundary, and whether a delayed revision can change interval membership. Bind the applicable rate card and pricing basis to the report snapshot. Verify that a rate-card update between summary and drilldown preserves reconciliation for the original snapshot.

8. **Define the Grok admission rules for incomplete and overlapping evidence.** Spec lines 21, 37, 47, 51, 74–76. Specify the report outcome when a durable completion and usage snapshot disagree, when either is missing, and when parent and nested usage overlap. Require qualification of concurrent prompts, cancellation, and forked or rewound histories before admitting affected usage. Test that a folded aggregate and its child usage cannot both contribute to totals, and expose a coverage gap when lineage or token overlap remains unresolved. #101 report, lines 38, 42–45.

9. **Make the Linux readiness and filesystem gates explicit.** Spec lines 11, 69, 76. Define the supported architecture and filesystem scope and require activation to fail closed when private-path enforcement or exclusive publication cannot be verified. Bind readiness to the loaded unit, the expected executable and same-user process incarnation, and a fresh matching heartbeat. State the expected logged-in, logout, and headless behavior, including how a missing user manager is reported. #102 report, lines 29–35, 41–44.

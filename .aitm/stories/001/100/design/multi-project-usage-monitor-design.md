# Multi-project agent usage monitor

This is the candidate specification for follow-on #100. The [Grok Build CLI spike](../../101/story.md) and [Linux compatibility spike](../../102/story.md) are evidence prerequisites for full spec acceptance. The [#83 design](../../../000/83/design/usage-capture-design.md) and [qualified Mac activation](../../../000/83/attachments/activation-receipt.json) are the baseline.

## Outcome

Kendrick can work in several registered projects and stories at once, with Codex, Claude Code and Grok Build CLI sessions in any combination. He can park a chat and return to it without keeping a separate polling process alive for it. The first usage report shows measured usage and estimated cost by project. Each project drills down by story, including a visible bucket for usage without a verified story. A project may depend on a story in another project. Each project's usage belongs to the work it performs.

#83 qualified one continuously running AITM project on macOS. Each installed service currently scans its own configured transcript roots and uses project-specific source identities. This design moves discovery and routing into one local service and keeps the existing project ledgers. #83's qualified capture already satisfies the usage prerequisite for Core. [C44 / #51](../../../000/51/story.md) remains a separate consumer of compatible exports.

The initial design covers local sources for Codex Desktop on macOS, Claude Code and Grok Build CLI. Linux qualification includes the supported local Codex CLI surface, Claude Code and Grok Build CLI. Qualify each supported OS and provider surface with live evidence before claiming support. Windows remains a later port and an eventual public release requirement. Browser Grok, cloud or remote capture, account billing reconciliation, automated historical import from unrelated projects and changes to AITM workflow authority are outside this design. The first report is local. A hosted or published viewer is separate.

## One local service, explicit project registrations

Run one `aitm-usage` background service per OS user. Keep one private registration and routing store outside Git, with a per-project ledger, project UUID and private key. A registration includes a display name, canonical repo identity, approved checkout and worktree paths, provider/source permissions and capture start. A repo origin helps an operator verify the association. The explicit registration is authoritative, including when the remote is renamed or several clones use different remote URLs. One project can register several physical checkouts. Reject overlapping physical checkout anchors across projects so the same directory cannot establish two automatic claims. Validate re-resolved paths and stable filesystem identity before trusting an anchor. Changing a registration takes effect at a recorded boundary and preserves existing attribution. No registration is created by discovering a Git repo under a home directory.

Provider installations and source roots are user-approved once and may serve several projects. Each project chooses which of those provider installations it accepts. Normalize discovery per provider installation so shared roots are watched once. Use provider-recorded checkout or explicit enrollment to admit a session segment. An outside reviewer can be admitted through a verified scope marker without turning that reviewer's whole checkout into a project anchor. A provider, session or file path from an untrusted hook is a discovery hint subject to the same allowlists and evidence checks. Unregistered activity is excluded from project collection. Persist normalized evidence, keyed references, durable cursors and sanitized diagnostics in private state. Keep prompts, responses, tool arguments, credentials and raw provider IDs out of persisted collector data and reports. Keep any raw filesystem paths needed for approved configuration private and omit them from exports.

## Request ownership and cross-project handoff

The unit of accounting is the smallest request or usage span the adapter can prove. Scope includes project UUID, stable story or draft identity, phase and participant, with optional role, attempt and review identity. Use #83's verified native request boundary and existing development owner generation rules. A verified scope marker can establish the project where checkout evidence is absent. An ordinary marker cannot silently override a contradictory project anchor. Keep project ownership, story scope and provider session identity independent. Project-qualified usage without sufficient story proof belongs in **Unattributed to a story**. Work explicitly marked as project-wide goes in **Project-wide work**. If no unique project is proven, hold the candidate out of all project totals and expose a sanitized routing or coverage reason. Ambiguous aggregates spanning several projects remain unallocated until there is finer evidence.

A session can work on several stories or projects over time. A handoff names the current and destination project, the destination scope and the relevant attempt or review authority. A user or authorized workflow acting for that session submits a dedicated handoff command. Validate the current scope, permission to enroll the session in the destination and the native receipt at the next proven request boundary. An accepted handoff closes the old scope at that same boundary. It can establish destination scope when the host continues to report the prior project's checkout, with the override limited to that session segment. Evidence of a third project's checkout is a conflict. A Develop owner still needs the destination's approved worktree, owner and generation proof. This command changes usage attribution only. Preserve prior requests and hold affected usage while a switch is pending or contradicted. Delayed revisions stay tied to their original requests. A shell tool's working directory, an open window, a branch name or a dependency mention alone cannot change attribution.

For example, a Codex chat in `ai-peer-review` opens a blocking defect in `ai-task-manager`. Work through the next verified scope switch belongs to the active `ai-peer-review` story. Work on the upstream fix and its package release belongs to the `ai-task-manager` defect after the switch, or from a separate explicitly bound chat. Downstream installation and verification belong to the `ai-peer-review` story. The dependency links the two qualified item identities. Reporting follows parent and draft-alias relationships within each project and keeps dependency edges out of cost rollups.

## Discovery, parking and recovery

Each enabled provider adapter maps available hooks and local file-change notifications to signals. A hook writes a minimal local wake or lifecycle notification and returns promptly. It uses the same adapter identity when the host runs a compatibility hook. Deduplicate and coalesce duplicate notifications by native host, session and turn or boundary when available. Use provider-native evidence to decide ordering and whether usage exists. A hook cannot create or charge usage. Scope commands still require their own durable native proof.

| Monitor state | Entry and collection behavior |
| --- | --- |
| Active | A prompt, launch, resume, scoped background event or source change schedules incremental reading for that stream. Track concurrent turns separately where the host exposes them. Check the changing source while activity continues. |
| Settling | Turn-end, interrupt, exit or explicit park triggers a final catch-up. Wait for a stable source checkpoint and leave unfinished requests marked partial. If another turn remains active, keep that turn scheduled. |
| Parked | Remove the session from the routine active queue. Retain source cursor, accepted scope and pending evidence. A new prompt, resume or file change schedules catch-up from the cursor. Preserve the old scope only where it still applies at the next verified boundary. |

Missing lifecycle signals or an unexpectedly quiet source can move the stream to low-priority monitoring after a bounded idle period. That is a scheduling decision. It grants no completion, pause, ownership release or permission to resume an AITM attempt. Delay, out-of-order events and a stale stop must never close a newer turn. A watch event can arrive after a final hook. Reopen the source when it changes so late usage, subagents and file rotations can be reconciled. Hooks can be absent, disabled or missed. On startup, watch overflow, sleep/wake and at a bounded fallback cadence, reconcile the authorized roots using file identity and metadata first. Read only new or changed sources from verified checkpoints. Prioritize active streams, cap work per pass and let the builder choose the queue, watch and backoff settings to meet the verification cases below.

When delayed proof may establish project ownership, retain a bounded hold with keyed source and boundary references, the earliest verified replay checkpoint and a sanitized reason. Keep usage for these holds in the provider source until ownership is proven. Discovery may advance only if the hold retains enough continuity to replay independently. A new proof schedules that replay. Retire the hold on proven assignment or exclusion. If provider retention or the hold limit prevents replay, record an explicit coverage gap and discard its replay state. Skip known unrelated activity.

## Provider adapters

Use a versioned adapter interface inside `aitm-usage`. It declares host surface and supported versions, discovery and cursor semantics, lifecycle capability, normalized observation identity and revisions, verifiable boundaries, token categories, model, pricing evidence and coverage gaps. Configuration enables adapters per provider installation and per project. A project can set a default driver. Author, reviewer or researcher is a session or scope property independent of host. Adapters are installed deliberately by the user. Project config selects a trusted installed adapter and approved source roots. Version the contract so new providers can be added without changing the reporter, project router or accounting rules.

- **Codex.** Carry forward #83's qualified Desktop counter and archive semantics. Establish local CLI compatibility on Linux using native fixtures and a live qualification run. Use documented hooks where the installed surface supports them, with change detection as a fallback. [Codex plugin hooks](https://developers.openai.com/plugins/build/plugins)
- **Claude Code.** Carry forward #83's request identities, streamed revisions, nested overlap checks and native boundary validation. Map start or resume, prompt, turn completion and session exit where available. [Claude Code hook reference](https://code.claude.com/docs/en/hooks)
- **Grok Build CLI.** The installed CLI exposes persisted per-turn usage through `grok usage <session-id>`. The predecessor AITM also has a Grok hook bridge. Qualify real native data for stable session and turn identity, token categories, model, retries or revisions, and the actual boundary granularity. Prefer a supported incremental source where it can be qualified. If Grok can prove only a whole turn, scope switches apply at the next proven turn, and a turn spanning conflicting scopes stays unallocated. Only use reported cost in the common estimate if its basis is established as comparable, otherwise compute from a versioned rate card where possible or show Unknown. [Grok hooks and plugins](https://docs.x.ai/build/features/skills-plugins-marketplaces#hooks) · [Grok Build usage history](https://x.ai/changelog/build)

## Durable routing and project ledgers

Before project pseudonymization, derive a private service-level identity from the provider namespace and verified native request lineage. Replayed, copied and archived versions of the same logical observation must resolve to one claim. For Codex preserve the verified stream, counter epoch and ordinal rules. Treat a provider retry with its own proven identity as separate usage. When continuity is unprovable, hold the overlapping span. Keep the service key and journal private. They are part of backup and recovery and do not enter per-project exports. Keep project-level pseudonyms and project export identities stable.

The service journal reserves one destination per canonical observation identity. In one journal transaction retain the claim, normalized pending revision and source progress needed for replay. Then write to the destination through its guarded ledger with a stable project observation key and idempotent revision. Acknowledge the route after confirming the durable project write. A restart retries any pending delivery. Crashes after reservation or after project commit must converge on one project entry. Once complete, retain only the routing metadata needed for deduplication and recovery. Treat contradictory revision content or ownership as a visible conflict. A later scope switch cannot move an earlier charge. Story corrections within a project use #83's evidence-backed revision history. Moving a settled observation between projects is separate reconciliation work. If stronger evidence disputes a settled claim, flag it and omit it from current combined attributed totals pending reconciliation. Preserve historical reports and route any already exported or Core-accepted conflict to an explicit reconciliation record. Never send a changed payload under an already accepted immutable Core key.

## Reports and compatibility

The first local interface is a read-only CLI report with machine-readable output. Given a time range, show each registered project's observed tokens and API-equivalent estimate in USD, count of unpriced or partial observations, and coverage status. Drill into a selected project by story, draft, project-wide work and unattributed story scope. Include optional provider, phase and role breakdowns. Show direct epic usage and inclusive rollup distinctly. Count each descendant once and resolve draft graduation through the recorded alias. Each project total reconciles to its direct story and draft totals plus the two project buckets. Never sum inclusive epic rows into that reconciliation. Keep a known zero distinguishable from unavailable data. Show pricing basis and keep actual billing and provider account quota separate.

A project write becomes visible to supported current reports and exports only after the service journal acknowledges it. The ACK records the project ledger sequence and exact accepted revision. A report pins one journal view and its published ledger sequences, then admits only revisions acknowledged in that view. A pending update leaves the previously published revision visible unless it is disputed. Hold disputed observations from current reports and compatible exports, with the reason visible as coverage or reconciliation state. Apply the same view to project summary and story drilldown. Keep #83 fixed-sequence exports reproducible at their original rate card. Use a versioned export for monitor-owned data, including new provider and availability fields. C44 remains the consumer of compatible project-scoped usage and retains its own acceptance and reconciliation checks. The local usage report works before Core or the viewer is available.

## Cutover and platforms

Adopt the existing production AITM UUID, key, database, scope history, registration and capture cutoff. Before changing supervision, back up the ledger and record its last committed source checkpoints, ledger sequence and fixed export. Briefly stop the existing writer while the new service takes custody. Use the same writer guard and refuse activation if a legacy writer still owns it. Resume existing streams at verified continuity with the established request-key algorithm. Reconcile observations written during the service stop once.

Before opening another project route, establish a verified baseline on shared provider roots. Admit to the new project only usage proven beyond its enrollment boundary. A copied, renamed or newly discovered source must prove continuity past that boundary or a new post-boundary origin. A new file path or timestamp alone is insufficient. Existing AITM history stays with its original ledger, and delayed revisions may update it only when they prove the original lineage and observation key. Project-keyed legacy references alone cannot seed the service-wide claim index. Hold ambiguous archives and any span that crosses a cutover or enrollment boundary without a measurable split, and report the gap. Opening a new registration never starts historical backfill.

Prove recovery of the service journal, its key and the project ledgers together before cutover. Preserve private evidence and the original fixed view. Restore the prior service from the verified pre-cutover state if activation fails before new writes. After the new service accepts usage, rollback requires tested format compatibility and preservation of those observations. Use forward recovery when that rollback cannot be proven.

Keep supervision, process verification, watches and secure filesystem operations behind OS boundaries. macOS uses one per-user LaunchAgent. Linux uses a user service on systemd hosts. The Linux port includes private path enforcement with access and default ACL checks, equivalent no-replace publication for inbox files and export directories, a stable per-user writer guard, durability, and process and heartbeat verification. Use one logical watch set per authorized root with recursive coverage, dynamic enrollment and metadata-first reconciliation after watch overflow. Bind service readiness to the loaded user unit and the actual same-user process incarnation. Qualify logged-in and headless lifecycle behavior on a real systemd user manager. The Linux spike ran pinned Codex, Claude Code and Grok Build binaries and exercised these primitives in an arm64 container. Authenticated provider traffic and systemd user-service operation remain separate release gates. An exact Linux Codex CLI version match with the Mac Desktop build does not prove a compatible scope marker. [Linux evidence](../../102/attachments/report.md) Windows can supply its own host lifecycle and storage mechanisms later. Keep the routing, provider contract and report semantics common. [systemd service documentation](https://www.freedesktop.org/software/systemd/man/latest/systemd.service.html)

## Verification required before delivery

- Register two separate repositories with the same issue number and at least two checkouts for one project. Run real overlapping Codex, Claude Code and Grok Build CLI sessions in the supported platform matrix. Verify all three roles, independent story attribution and cross-project handoff with a dependency. Verify an unmarked review, a project-wide task and an ambiguous project claim. The sums reconcile and no observation is charged to two projects.
- Exercise park and resume in the same session, a late append after stop, a background write while parked, a missing hook, a watch overflow and stale or duplicated notifications. Verify one observation per proven request across restart, copies, archive moves, both marker arrival orders and crash points around reservation, project commit and ACK.
- Exercise a captured workload with at least two active streams and 50 parked sessions. For a clean idle interval spanning a healthy reconciliation cycle, assert zero transcript payload reads for unchanged parked sources. Increasing registered project count with the same enabled provider roots must not increase source enumerations per reconciliation. Verify that a single changed parked source is picked up without reading unrelated parked payloads. Record wake-to-report latency, CPU, memory and file reads under sustained activity and backlog before setting release budgets.
- Rehearse cutover and recovery with a copy of representative #83 state. Verify exact original export parity, unchanged source identities, no lease overlap, new writes after cutover and recovery of pending routes. Reintroduce old transcript bytes at a new path and prove they cannot be claimed by another project. Compare reports and exports before and after route ACK and a dispute. Use versioned fixtures and controlled real transcripts to qualify provider support. Qualifying Grok requires story attribution across at least two native turns. When any of the three adapters lacks proven story attribution on a target surface, report that limitation and keep the three-provider qualification gate open.

## Design choices for review

Explicit enrollment, CLI-first reporting, one service journal with existing project ledgers, and wake signals plus bounded reconciliation are proposed defaults. The builder can choose the local IPC, file-watch APIs, incremental buffering and scheduling thresholds after measuring representative loads. A plan must qualify Grok's usage and scope boundaries, the Linux provider surfaces and migration continuity early. This draft does not grant implementation or production cutover authority.

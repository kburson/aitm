# Multi-project agent usage monitor

This specification extends the delivered #83 collector under follow-on #100. It uses the completed [Grok Build CLI evidence](../../101/attachments/report.md) and [Linux compatibility evidence](../../102/attachments/report.md). The [#83 design](../../../000/83/design/usage-capture-design.md) and [qualified Mac activation](../../../000/83/attachments/activation-receipt.json) are the baseline.

## Outcome

Kendrick can work in several registered projects and stories at once, with Codex, Claude Code and Grok Build CLI sessions in any combination. He can park a chat and return to it without keeping a separate polling process alive for it. The first usage report shows measured usage and estimated cost by project. Each project drills down by story, including a visible bucket for usage without a verified story. A project may depend on a story in another project. Each project's usage belongs to the work it performs.

#83 qualified one continuously running AITM project on macOS. Each installed service currently scans its own configured transcript roots and uses project-specific source identities. This design moves discovery and routing into one local service and keeps the existing project ledgers. #83's qualified capture already satisfies the usage prerequisite for Core. [C44 / #51](../../../000/51/story.md) remains a separate consumer of compatible exports.

The initial design covers local sources for Codex Desktop on macOS, Claude Code and Grok Build CLI. The macOS Codex CLI is outside the initial qualification matrix even when its rollout shares the Desktop source root. Linux qualification includes the supported local Codex CLI surface, Claude Code and Grok Build CLI. Qualify each supported OS and provider surface with live evidence before claiming support. Windows remains a later port and an eventual public release requirement. Browser Grok, cloud or remote capture, account billing reconciliation, automated historical import from unrelated projects and changes to AITM workflow authority are outside this design. The first report is local. A hosted or published viewer is separate.

## One local service, explicit project registrations

Run one `aitm-usage` background service per OS user. Use a stable user-scoped coordinator lease so a second service or manual writer cannot route concurrently. Keep one private registration and routing store outside Git, with a per-project ledger, project UUID and private key. A registration includes a display name, canonical repo identity, approved checkout and worktree paths, provider/source permissions and capture start. A repo origin helps an operator verify the association. The explicit registration is authoritative, including when the remote is renamed or several clones use different remote URLs. One project can register several physical checkouts. Reject identical or ancestor/descendant physical checkout anchors across different projects so the same directory cannot establish two automatic claims. Validate re-resolved paths and stable filesystem identity before trusting an anchor. Registration and provider permission changes take effect at a recorded source boundary per affected stream. Decide eligibility at the original usage boundary. A disabled interval stays excluded after re-enrollment, even if its records arrive later. Keep already admitted pending writes and revisions to eligible earlier usage when the evidence remains authorized to read. Revoked source permission ends further reads for that project. Exclude activity proven to occur after disablement. An in-flight span that crosses the boundary and cannot be split becomes a coverage gap. No registration is created by discovering a Git repo under a home directory.

Provider installations and source roots are user-approved once and may serve several projects. Each project chooses which of those provider installations it accepts. Normalize discovery per provider installation so shared roots are watched once. Validate the recorded host surface, client version and format against the adapter’s qualified matrix. In an approved shared root, a source with an unsupported or unproven surface or version contributes no usage totals. Expose a sanitized coverage reason for affected eligible context and avoid disclosing unrelated session details. Use provider-recorded checkout or explicit enrollment to admit a session segment. An outside reviewer can be admitted through a verified scope marker without turning that reviewer's whole checkout into a project anchor. A provider, session or file path from an untrusted hook is a discovery hint subject to the same allowlists and evidence checks. Only an owner-approved integration or operator command may propose scope. Authenticate the scope proposal, then verify its link to a native boundary. Repository configuration and a claimed hook event alone carry no enrollment authority. The OS account and approved integrations are trusted. The monitor cannot protect its private files from an attacker that already controls that account. Unregistered activity is excluded from project collection. Persist normalized evidence, keyed references, durable cursors and sanitized diagnostics in private state. Keep prompts, responses, tool arguments, credentials and raw provider IDs out of persisted collector data and reports. Keep any raw filesystem paths needed for approved configuration private and omit them from exports.

## Request ownership and cross-project handoff

The unit of accounting is the smallest request or usage span the adapter can prove. Scope includes project UUID, stable story or draft identity, phase and participant, with optional role, attempt and review identity. Use #83's verified native request boundary and existing development owner generation rules. A verified scope marker can establish the project where checkout evidence is absent. A verified ordinary marker for project A in project B’s registered checkout is a conflict. Hold the affected usage out of both project totals until a verified handoff or evidence-backed disposition resolves it. If no explicit scope exists, the verified anchor project is the handoff’s current project at initial generation zero. The dedicated handoff is required to override that anchor. Keep project ownership, story scope and provider session identity independent. Project-qualified usage without sufficient story proof belongs in **Unattributed to a story**. Work explicitly marked as project-wide goes in **Project-wide work**. If no unique project is proven, hold the candidate out of all project totals and expose a sanitized routing or coverage reason. Ambiguous aggregates spanning several projects remain unallocated until there is finer evidence.

A session can work on several stories or projects over time. A handoff names the current and destination project, the destination scope and the relevant attempt or review authority. A user or authorized workflow acting for that session submits a dedicated handoff command. Verify the current scope generation, permission to enroll the session in the destination, and the command’s native receipt. The handoff takes effect at the first supported request or turn boundary after that receipt in the same stream. An accepted handoff closes the old scope at that same boundary. Deduplicate exact retries by command identity. Check a proposal against the scope generation in force immediately before its target boundary, independent of delivery order. A proposal for an already superseded generation at a later boundary is stale. A second independently valid proposal for the same generation and boundary is a conflict even if the first route was acknowledged. Dispute the affected requests from that boundary until scope is independently proven again. Previously published snapshots retain their original view. Current reports and compatible exports hold the disputed span, with reconciliation evidence for any already delivered rows. An evidence-backed disposition can resolve the conflict. A settled cross-project move still requires explicit reconciliation. An explicit handoff can supersede a previously verified stale checkout carried by the session. For A→B→C while the host still records A, the second handoff must name current B, prove the retained A checkout is unchanged, and bind C at the next verified boundary. A newly observed checkout outside those proven relationships creates a conflict. A Develop owner still needs the destination's approved worktree, owner and generation proof. This command changes usage attribution only. Preserve prior requests and hold affected usage while a switch is pending or contradicted. On rejection, resume the previous scope only where native continuity and absence of another unresolved claim prove it applies. Otherwise resolve the held span through verified evidence or report a coverage gap when the hold expires. Delayed revisions stay tied to their original requests. A shell tool's working directory, an open window, a branch name or a dependency mention alone cannot change attribution.

For example, a Codex chat in `ai-peer-review` opens a blocking defect in `ai-task-manager`. Work before the next verified scope switch belongs to the active `ai-peer-review` story. Work on the upstream fix and its package release belongs to the `ai-task-manager` defect after the switch, or from a separate explicitly bound chat. Downstream installation and verification belong to the `ai-peer-review` story. The dependency links the two qualified item identities. Reporting follows parent and draft-alias relationships within each project and keeps dependency edges out of cost rollups.

## Discovery, parking and recovery

Each enabled provider adapter maps available hooks and local file-change notifications to signals. A hook sends a minimal local wake or lifecycle notification and returns promptly. Resolve raw locators transiently through approved local ingress. Persist only keyed session and source references and allowlisted lifecycle metadata. Retire consumed wake records after reconciliation. Collector downtime or a dropped wake cannot block the provider turn. Reconcile from native evidence after a restart. It uses the same adapter identity when the host runs a compatibility hook. Deduplicate and coalesce duplicate notifications by native host, session and turn or boundary when available. Use provider-native evidence to decide ordering and whether usage exists. A hook cannot create or charge usage. Scope commands still require their own durable native proof.

| Monitor state | Entry and collection behavior |
| --- | --- |
| Active | A prompt, launch, resume, scoped background event or source change schedules incremental reading for that stream. Track concurrent turns separately where the host exposes them. Check the changing source while activity continues. |
| Settling | Turn-end, interrupt, exit or an operator or authorized workflow park triggers a final catch-up. Park carries scheduling intent only. Wait for a stable source checkpoint and leave unfinished requests marked partial. If another turn remains active, keep that turn scheduled. |
| Parked | Remove the session from the routine active queue. Retain source cursor, accepted scope and pending evidence. A new prompt, resume or file change schedules catch-up from the cursor. Preserve the old scope only where it still applies at the next verified boundary. |

Missing lifecycle signals or an unexpectedly quiet source can move the stream to low-priority monitoring after a bounded idle period. That is a scheduling decision. It grants no completion, pause, ownership release or permission to resume an AITM attempt. Delay, out-of-order events and a stale stop must never close a newer turn. A watch event can arrive after a final hook. Reopen the source when it changes so late usage, subagents and file rotations can be reconciled. Hooks can be absent, disabled or missed. On startup, watch overflow, sleep/wake and at a bounded fallback cadence, reconcile the authorized roots using file identity and metadata first. Read only new or changed sources from verified checkpoints. Prioritize active streams, cap work per pass and let the builder choose the queue, watch and backoff settings to meet the verification cases below.

When delayed proof may establish project ownership, retain a bounded hold with keyed source and boundary references, the earliest verified replay checkpoint and a sanitized reason. Keep usage for these holds in the provider source until ownership is proven. Discovery may advance only if the hold retains enough continuity to replay independently. A new proof schedules that replay. Retire the hold on proven assignment or exclusion. If provider retention or the hold limit prevents replay, record an explicit coverage gap and discard its replay state. Skip known unrelated activity.

## Provider adapters

Use a versioned adapter interface inside `aitm-usage`. It declares host surface and supported versions, discovery and cursor semantics, lifecycle capability, normalized observation identity and revisions, verifiable boundaries, a versioned observation time basis, token categories, model, pricing evidence and coverage gaps. Configuration enables adapters per provider installation and per project. A project can set a default driver. Author, reviewer or researcher is a session or scope property independent of host. Adapters are installed deliberately by the user. Project config selects a trusted installed adapter and approved source roots. Version the contract so new providers can be added without changing the reporter, project router or accounting rules.

- **Codex.** Carry forward #83's qualified Desktop counter and archive semantics. Establish local CLI compatibility on Linux using native fixtures and a live qualification run. Use documented hooks where the installed surface supports them, with change detection as a fallback. [Codex plugin hooks](https://developers.openai.com/plugins/build/plugins)
- **Claude Code.** Carry forward #83's request identities, streamed revisions, nested overlap checks and native boundary validation. Map start or resume, prompt, turn completion and session exit where available. [Claude Code hook reference](https://code.claude.com/docs/en/hooks)
- **Grok Build CLI.** The controlled macOS 1.0.77 run joined two different synthetic scope receipts to two distinct native prompt IDs and durable `turn_completed` records in one session across explicit resume. Both completions reconciled with `grok usage <session-id>` and repeated reads returned identical usage. This establishes a candidate whole-turn carrier. Use verified native completion time for its report interval so a missing prompt hook does not erase an otherwise eligible turn. The product must authenticate each marker and verify the same native prompt lineage before accepting its project or story. Qualify project ownership separately using proven checkout context or explicit enrollment. If both are missing, hold the turn outside project totals. A production hook must run under the owner’s approval for its registered scope. Use a verified completion as the observation and the persisted usage snapshot for corroboration. Session totals, current ACP counters and presentation ordinals cannot create additive observations. Validate token semantics per surface because persisted input includes cache and headless uncached input uses a different schema. Apply a scope switch at the next proven turn. Hold an aggregate that spans conflicting projects. Report provider cost ticks separately unless their basis is established as comparable, and compute the common estimate from a versioned rate card where the model and token evidence support it. Retain Unknown otherwise. A complete qualified native completion can count when the snapshot is missing, with a corroboration gap. A snapshot without verified native prompt lineage contributes no usage to attributed totals. Contradictory completions and snapshots stay disputed until verified supersession resolves them. Prefer proven nonoverlapping detail for nested work. Count a folded parent once only if its coverage and scope are independently established, with all included child usage suppressed. Hold any unresolved overlap as a coverage gap. Qualify copied, inherited or rewound history, concurrent prompts, missing hooks, cancellation, late writes, and native Linux capture separately before admitting affected usage. [Grok spike](../../101/attachments/report.md) · [Grok hooks and plugins](https://docs.x.ai/build/features/skills-plugins-marketplaces#hooks)

## Durable routing and project ledgers

Before project pseudonymization, derive a private service-level identity from the provider namespace and verified native request lineage. Replayed, copied and archived versions of the same logical observation must resolve to one claim. For Codex preserve the verified stream, counter epoch and ordinal rules. Treat a provider retry with its own proven identity as separate usage. When continuity is unprovable, hold the overlapping span. Keep the service key and journal private. They are part of backup and recovery and do not enter per-project exports. Keep project-level pseudonyms and project export identities stable.

The service journal reserves one destination per canonical observation identity. In one journal transaction retain the claim, normalized pending revision and source progress needed for replay. Then write to the destination through its guarded ledger with a stable project observation key and idempotent revision. Acknowledge the route after confirming the durable project write. A restart retries any pending delivery. Crashes after reservation or after project commit must converge on one project entry. Once complete, retain only the routing metadata needed for deduplication and recovery. If a project ledger is unavailable, keep its reserved routes pending and report the gap. Bound pending capacity per destination and reserve scheduling capacity for independent healthy project streams. A full destination queue must not delay independent healthy streams. A shared stream can stop at its last replayable boundary if it cannot safely retain a pending revision, even if later requests belong to a healthy project. Expose the stalled stream and dependent coverage gap, then replay from that boundary when capacity returns. Never advance past unstaged evidence.

Accept a newer revision only when verified native source order or provider correction lineage proves it supersedes the current revision. Ignore identical replay and proven older revisions. If two revisions are incomparable or conflict under the same identity, hold the disputed observation. The guarded project write and journal acknowledgement both compare the expected lineage and preserve the newest published revision across restarts and stale acknowledgements. Treat contradictory revision content or ownership as a visible conflict. A later scope switch cannot move an earlier charge. Story corrections within a project use #83's evidence-backed revision history. Moving a settled observation between projects is separate reconciliation work. If stronger evidence disputes a settled claim, flag it and omit it from current combined attributed totals pending reconciliation. Preserve historical reports and route any already exported or Core-accepted conflict to an explicit reconciliation record. Never send a changed payload under an already accepted immutable Core key. When a verified correction, including a time correction, changes such a payload, retain the original acceptance receipt and payload history, and emit a reconciliation disposition for the corrected revision. Hold the corrected payload from compatible export until a supported correction or reconciliation is accepted. Current local reports show the corrected observation once. Earlier report snapshots retain their original time assignment. The corrected revision cannot become a second charge.

## Reports and compatibility

The first local interface is a read-only CLI report with machine-readable output. For a requested UTC interval with an inclusive start and exclusive end, use the adapter’s declared and recorded observation time basis. Prefer a verified native start boundary where the qualified surface exposes one. Otherwise use the verified native completion or qualified usage-event time declared for that surface. Freeze the selected basis with the observation. Allocate an indivisible span once at its selected time, even when it crosses the end of the interval. Preserve the stored observation time of legacy rows. A later usage revision retains interval membership. Evidence-backed time corrections change membership only in a new published snapshot. Show each registered project’s observed tokens, API-equivalent estimate in USD, count of unpriced or partial observations, and coverage status. Mark an unknown observation time as a coverage gap outside the requested interval totals. Label a subtotal as partial when missing quantities or prices prevent a complete total. Drill into a selected project by story, draft, project-wide work and unattributed story scope. Include optional provider, phase and role breakdowns. Show direct epic usage and inclusive rollup distinctly. Count each descendant once and resolve draft graduation through the recorded alias. Each project total reconciles to its direct story and draft totals plus the two project buckets. Never sum inclusive epic rows into that reconciliation. Keep a known zero distinguishable from unavailable data. Show pricing basis and keep actual billing and provider account quota separate.

A project write becomes visible to supported current reports and exports only after the service journal acknowledges it and the publication recovery fence is durable. Before exposing any new publication view, durably record its monotonic watermark and scope and route decision digests in a private recovery log kept outside rollback snapshots. A recovery fence written before an interrupted publication can block replay, but cannot prove the interrupted view was exposed. Record the exact receiver identity, key and payload digest in that fence before sending a compatible export. Reconcile an uncertain export against the receiver before retrying it. The ACK records the project ledger sequence and exact accepted revision. At cutover, record the verified existing AITM ledger sequence as a grandfathered publication baseline in the journal. Include that baseline in the first monitor report and compatible export without fabricating individual ACKs or service-wide legacy identities. New writes and late revisions beyond the baseline need the normal acknowledgement. A report pins one journal view and its published ledger sequences, then admits only revisions acknowledged in that view. A pending update leaves the previously published revision visible unless it is disputed. Hold disputed observations from current reports and compatible exports, with the reason visible as coverage or reconciliation state. Return a snapshot identifier from the summary and accept it on drilldown, so separate invocations can use the same journal and project view, time window and exact rate card and pricing basis. A rate-card update opens a new view. Earlier snapshots retain their pricing until the snapshot becomes unavailable. Include scope and relationship revisions visible at that view. A requested snapshot whose inputs have expired returns an explicit unavailable result. Keep #83 fixed-sequence exports reproducible at their original rate card. Use a versioned export for monitor-owned data, including new provider and availability fields. C44 remains the consumer of compatible project-scoped usage and retains its own acceptance and reconciliation checks. The local usage report works before Core or the viewer is available.

## Cutover and platforms

Adopt the existing production AITM UUID, key, database, scope history, registration and capture cutoff. Before changing supervision, back up the ledger and record its last committed source checkpoints, ledger sequence and fixed export. Briefly stop the existing writer while the new service takes custody. Use the same writer guard and refuse activation if a legacy writer still owns it. Resume existing streams at verified continuity with the established request-key algorithm. Reconcile observations written during the service stop once.

Before opening another project route, establish a verified baseline on shared provider roots. Admit to the new project only usage proven beyond its enrollment boundary. A copied, renamed or newly discovered source must prove continuity past that boundary or a new post-boundary origin. A new file path or timestamp alone is insufficient. Existing AITM history stays with its original ledger, and delayed revisions may update it only when they prove the original lineage and observation key. Project-keyed legacy references alone cannot seed the service-wide claim index. Hold ambiguous archives and any span that crosses a cutover or enrollment boundary without a measurable split, and report the gap. Opening a new registration never starts historical backfill.

Prove recovery of the service journal, its key and the project ledgers together before cutover. Capture the backup at a coordinated publication boundary and retain pending routes with their replay metadata. Reject a mixed restore that cannot match the journal to its project ledger identities and checkpoints. A restored set can still be older than delivered exports or a scope change. Before replay, verify the current monotonic tail of the independently retained recovery log and compare it with the restored watermark and trusted publication, scope and export receipts. A backup and a copy of the same old recovery log cannot establish currentness. If the independent tail is missing, unverifiable or ahead of evidence that can be reconciled, stop affected replay at the last proven common boundary. Reconstruct the missing authenticated scope and publication decisions before releasing affected replay. An already accepted Core key keeps its accepted identity. If a current high-water mark or the missing decisions cannot be proven, hold affected spans and expose the recovery gap. A verified new baseline can resume prospective capture without reassigning the gap. Preserve private evidence and the original fixed view. Restore the prior service from the verified pre-cutover state if activation fails before new writes. After the new service accepts usage, rollback requires tested format compatibility and preservation of those observations. Use forward recovery when that rollback cannot be proven.

Keep supervision, process verification, watches and secure filesystem operations behind OS boundaries. macOS uses one per-user LaunchAgent. The initial Linux qualification target is arm64 and x86-64 with a systemd user manager and a local ext4 state volume. Claim each target only after its own verification. Reject activation when private-path or exclusive-publication semantics cannot be proven. The Linux port includes private path enforcement with access and default ACL checks, equivalent no-replace publication for inbox files and export directories, a stable per-user writer guard, durability, and process and heartbeat verification. Use one logical watch set per authorized root with recursive coverage, dynamic enrollment and metadata-first reconciliation after watch overflow. Bind service readiness to the loaded user unit, verified executable and same-user process incarnation with a fresh matching heartbeat. Enable the service within the logged-in user manager. Logout follows the manager’s lifetime. Headless continuation requires a working user manager and any operator-approved lingering policy. Report an unavailable user manager explicitly and verify logged-in, logout and headless behavior on a real systemd user manager. The Linux spike ran pinned Codex, Claude Code and Grok Build binaries and exercised these primitives in an arm64 container. Authenticated provider traffic and systemd user-service operation remain separate release gates. Qualify the Linux Codex CLI scope marker independently of Mac Desktop even when the versions match. Windows can supply its own host lifecycle and storage mechanisms later. Keep the routing, provider contract and report semantics common. ## Design choices for review

Explicit enrollment, CLI-first reporting, one service journal with existing project ledgers, and wake signals plus bounded reconciliation are proposed defaults. The builder can choose the local IPC, file-watch APIs, incremental buffering and scheduling thresholds after measuring representative loads. The implementation plan must carry forward production Grok admission and platform qualification, the Linux provider surfaces and migration continuity. Implementation and production cutover require separate authorization.

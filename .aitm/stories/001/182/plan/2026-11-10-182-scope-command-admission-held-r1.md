## Grant and reader admission

An owner-authorized coordinator writer provisions a scoped grant for one registered project, current pinned project directory and ledger key, permitted route and operation. Keep at most one eligible legacy grant for an adopted ledger. An explicit request selects a public opaque grant UUID. The private credential is loaded only by a pinned, lease-free read of already initialized authority and never comes from a repository, a provider transcript, an untrusted environment variable or a request file. Issuance and compatible-reader advertisement require the coordinator lease. No CLI command can issue a grant, generate a key or install a reader.

Use separate domain tags for grants, reader witness and command seal. Derive the grant secret for the selected generation from existing initialized private authority and give the producer only the scoped credential. Bind witness authentication to grant and protocol, project, physical registry and project identity, ledger key, adopted identity for the compatibility route, an actual verified reader capability, and a bounded validity window. A fixture uses the actual typed inbox reader under the writer, then proves it can verify the exact signed scope publication. A bare registry version, a pid, a public path or a static configuration flag supplies no witness. The producer checks grant and witness under the existing monitor publication lock immediately before acknowledging any queue operation. Witness renew/revoke takes that same lock. Short expiry prevents a stopped compatible reader leaving indefinite admission; the later coordinator supplies the live capability and renewal. A missing, invalid, stale, revoked or mismatched witness returns a sanitized unavailable result, creates no queue entry and never reports queued. Bound unconsumed scope entries per inbox at 256, preserving identical pending retry and control-command capacity. Keep private credentials and raw provider data out of queue and evidence.

Use the existing M06 account inbox, publication lock, ordinal allocator, digest and exact per-ID filename. A closed typed scope variant preserves exact bytes for all existing M06 control envelopes and terminal receipts. The mixed queue validates structural encoding, UUID and protocol. The M06 drain skips every structurally valid scope variant before its normal receipt and mutation paths. An invalid scope seal has no authority and cannot block unrelated control processing. It never removes them or blocks independent controls behind them. Use the same read path to prove that the authenticated compatible reader can read the proposal. No scope application or retirement is part of this slice. A producer retry with exact immutable request and grant bytes reuses the original ID and order. ## Explicit and adopted commands

Add `aitm-usage monitor scope mark|handoff|dispose --request FILE` with optional `--json` for native proof and no `--request-id`. Set `allow_abbrev=False` for these leaf parsers. Reuse the bounded pinned owner-config parser, canonical UUID from the file, and the existing `Scope` and development binding types. Strict action-specific request objects carry the chosen grant and the immutable Mark, Handoff or Disposition fields except the native receipt reference. M11 derives that reference from the queued command UUID using the trusted source authority. A typed Handoff uses the current project for the grant, validates the registered destination separately and carries exact before-generation and optional retained checkout. Reject unmatched action or unknown fields before publishing. Exact successful JSON remains `{"command_id": "<uuid>", "status": "queued"}`; sanitized refusal contains no queued acknowledgement. Return ordinary terminal state through the same status shape.

Preserve the five legacy invocations and their output. Select the adopted route from the verified pinned ledger before writes. Legacy factories parse and verify the invoking provider and command with no session memo writes. If initially pre-adoption, take the same stable legacy publication lock M16 uses and recheck adoption, then validate and write the Claude session memo and command under that lock. Under the reviewed M16 protocol, a committed adoption holds and leaves this same pinned inbox in place. Never take the monitor publication lock while retaining the legacy lock. If adoption wins, release the legacy lock and submit the original typed legacy envelope through the admitted monitor route, without any legacy memo or command write. Match the active adopted identity, key and grant in the monitor-locked admission check. Read-only legacy receipts and exact pre-adoption semantics remain compatible. Preserve marker, binding and correction IDs on retry. Every independent `item alias` and `item parent` invocation still generates its own UUID.

Recognize only the exact canonical `aitm-usage monitor scope <action> --request <absolute FILE> --json` native call and its successful exact queued receipt. Add this grammar only in neutral Codex and Claude readers with existing verified tool, session, native position, exit and receipt context. The Codex Desktop wrapper, Claude Bash tool and verified explicit native session context remain required. Legacy readers and their invocation guards stay on the old grammar. A queued receipt joins only the first native target through the delivered M07a rules. No monitor source or service starts in this leaf. An M07a terminal hold can return a durable `ProofHold`, while its immediate retry result may be a rejected disposition. M11 must preserve that distinction and the first stored outcome.

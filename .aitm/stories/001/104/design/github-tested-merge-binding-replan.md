## Decision and limits

Keep the story branch and its normal same-repository PR into the declared target. Keep the canonical ordinary `pull_request` workflow and its stable `aitm-ci` job. GitHub creates a temporary merge for Actions. The closure owner verifies a GitHub Actions OIDC-backed Sigstore certificate that binds the canonical run and attempt to the temporary merge SHA. There are no extra CI branches, copied merges, branch-management workarounds or direct pushes to protected targets.

In [draft PR #107](https://github.com/kburson/aitm/pull/107), the source commit `d34921e` had one parent. GitHub's [temporary test merge](https://github.com/kburson/aitm/commit/e092c5f387db77d8eb7ac897f801f442097f6b6c) at `refs/pull/107/merge` has trunk `f80f226` as first parent and the source head as second. Neither object landed on trunk during the probe. GitHub's run, suite and job metadata named the source head. The runner's printed merge SHA and the live PR merge field agreed, but neither established an independent attempt-to-merge binding.

This amendment supplies that missing proof for #104–#106. It preserves #103's ordinary PR delivery and the historical design and plans. The manual bootstrap assumes trusted same-repository writers. For changes to workflow or reachable job controls, review the exact source and effective permissions before the authorized push that can trigger Actions. GitHub does not enforce that preflight on other branch writers. For this initial route, hold fork or other PRs lacking the same-repository identity and permission boundary. GitHub currently reports `kburson/aitm` as public. Artifact attestations are available to public repos on current GitHub plans. Before any probe, confirm visibility and applicable account entitlement. If private or internal without GitHub Enterprise Cloud, stop as infeasible. Any switch away from the public route or any settings change requires separate review. ## Why this identity is trustworthy

GitHub documents the ordinary open PR's merge ref and `GITHUB_SHA`. Its Actions OIDC issuer supplies certificate identity claims through Fulcio. Fulcio maps the OIDC `sha`, `ref`, repository ID, `workflow_sha`, event and run ID/attempt to signed certificate extensions. The certificate can bind the source and invocation independently of the candidate's logs, JSON and SLSA predicate. The expected PR-specific ref is `refs/pull/<number>/merge` and the exact source digest must equal the live raw test merge. The exact values still require a live proof in this repository using the actual certificate and independently retrieved GitHub metadata. [GitHub PR event](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#how-the-merge-branch-affects-your-workflow) · [Fulcio claim mapping](https://github.com/sigstore/fulcio/blob/main/docs/oid-info.md) · [GitHub CLI verification](https://cli.github.com/manual/gh_attestation_verify)

Use a GitHub artifact attestation for the exact bytes of a small sanitized evidence file. The Sigstore bundle supports verification after the OIDC token expires. Verify the signature, trusted Fulcio certificate and authenticated timestamp/transparency evidence with the pinned GitHub CLI verifier and its trusted roots. Plain OIDC bearer tokens are short-lived credentials and stay out of logs and artifacts. A merge object by itself identifies its parents, while an unsigned assertion about that object cannot identify which run attempted it. [GitHub attestation action](https://github.com/actions/attest) · [Sigstore security model](https://github.com/sigstore/fulcio/blob/main/docs/security-model.md)

A read-only check of the official attestation action's ordinary PR #532 demonstrated the binding. For run `42272300446` attempt `1`, GitHub CLI `2.97.0` verified the logged Sigstore bundle against its downloaded subject and trusted roots. The verified certificate named `refs/pull/532/merge`, source/config/signer digest `4445eeec781e30d059157650d3bf555a64045eb9`, and the exact run-attempt URI. The authenticated API associated the run with head `ebc4745a7c704a753ca9dd09ecdb1b2ac98333c6`. The raw merge's first parent was the event base and its second was that head. Verification refused the PR head as expected source digest, and the verified invocation did not match attempt 2. The example uses the action's test GitHub Sigstore instance and a release predicate. #104 must still prove the default public instance, ordinary file-provenance subject and two-job handoff on its own PR. [Official action example run](https://github.com/actions/attest/actions/runs/42272300446/attempts/1) · [Signing job](https://github.com/actions/attest/actions/runs/42272300446/job/128079669034).

## Exact verification

1. From the trusted target, authenticate the repository and immutable repo ID, live open PR and its same-repository head, declared target and its live branch ref, canonical workflow ID/path, run, latest attempt, GitHub Actions check suite and required attempt jobs. Select the newest canonical ordinary PR run matching PR number and event base/head, by the original run creation time and run ID. Read its latest attempt after selection. Missing or failed evidence on that attempt cannot be masked by an older run. API run, suite and job head SHAs must match the PR head. Bind job IDs to the GitHub Actions check records and require every applicable job exactly once with success in `/actions/runs/<id>/attempts/<n>/jobs`. Require each record’s `run_id` and `run_attempt` to match and its start timestamp to be at or after that attempt’s authenticated `run_started_at`. Missing or earlier jobs, including carried-over successes, hold the gate.
2. Read GitHub's current `refs/pull/<pr>/merge` and authenticated raw commit object. Require its SHA to equal the current PR merge SHA and its exactly two ordered parents to match the authenticated event base/head and live target/head. Record the candidate tree and gate-control blob IDs. An unavailable or inconsistent view holds the gate. A source head, alternate or locally reconstructed merge, or same-tree commit with a different SHA is ineligible.
3. Retrieve only the selected run's exact attempt artifact and verify GitHub artifact association, name, expiry and archive digest before reading it. Use an explicit allowlist of per-attempt intermediate and final artifact names. Known older attempt artifacts remain historical. A name collision, duplicate or unexpected artifact holds the gate. GitHub’s artifact association alone identifies only the run. The verified certificate invocation and signed subject digest supply the binding of these evidence bytes to the exact attempt. Bound the download and unpack only the two allowlisted regular file members, each at most 1 MiB. Reject extra or duplicate entries, traversal, links, unexpected files or malformed ZIPs. Never extract using candidate-chosen paths. Use pinned `gh attestation verify` with the local bundle, expected repo, signer workflow, issuer `https://token.actions.githubusercontent.com`, exact source digest/ref, hosted runner restriction and SLSA provenance type. Use trust roots from the trusted verifier environment and never from the candidate bundle or archive. Require one verified result. Match certificate claims for numeric source repository ID, Build Config URI/path and digest, Build Signer workflow and digest, `pull_request` trigger and exact Run Invocation URI `https://github.com/<owner>/<repo>/actions/runs/<id>/attempts/<n>`. For the top-level nonreusable canonical workflow expect both configuration and signer digests to equal the selected merge and verify its workflow blob against the reviewed control. Refuse any missing or mismatched signed value. Compare only authenticated certificate extensions for these identities, never values in the signed predicate. A subject digest verifies the JSON bytes, and the JSON still supplies only reported lane, checkout and product evidence.
4. Independently compare reported head/base/tested SHA/tree, run/attempt and checkout receipts against trusted observations. Require each candidate lane to pin and verify its checkout SHA before work, and the isolated baseline lane to pin the trusted first parent. The signature binds workflow identity and evidence bytes. The approved workflow controls and authenticated required job results establish what was run. Complete the control-blob review and owner disposition before verification and recheck before merge. GitHub reruns preserve the original event SHA and ref. A full rerun is eligible only while that original merge still equals the live merge. It needs all required jobs from its own attempt and a new bundle. Partial reruns, carried-over jobs, replay from another attempt and mismatched bytes are ineligible. [GitHub rerun semantics](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/re-run-workflows-and-jobs).
5. If the live head, base, target or merge moves, the old evidence stays historical. After movement, require a new `synchronize` from an allowed source-branch update against the target or an authorized `reopened` event when no source update is needed. A rerun or PR metadata edit cannot refresh the candidate. The #104 closure owner performs steps 1–5 manually with pinned `gh` and trusted roots and retains sanitized commands, result fields and digests before #105 exists. Before a normal GitHub merge commit, reread the exact evidence and use the expected-head guard with trunk rules in force. Coordinate merges into the same target. GitHub's merge API guards head only. Verify the delivered commit's ordered parents and tree after merge. If the target moved in the final interval, hold delivery and escalate the discrepancy without automatic retry or rollback. [GitHub merge endpoint](https://docs.github.com/en/rest/pulls/pulls#merge-a-pull-request)

## Workflow controls

- CI stays on `pull_request` and trunk `push`, with normal same-repository validation on declared targets, no workflow-wide path filter and existing policy for jobs and concurrency. Pin action SHAs and the verifier version, use hosted disposable runners, and keep checkout credentials disabled. Test, build, lint and base-evidence jobs remain read-only and lack identity-token and attestation permissions. Require the real qualified serial Darwin suite, the locked wheel smoke, trusted baseline and subprocess evidence.
- Keep the original single aggregate predicate over required jobs in the read-only evidence collector. It produces the existing sanitized `candidate.json` with run, attempt, PR, head/base/tested identities, tree, lane checkout and product evidence. Give the isolated `aitm-ci` signing job only the permissions required by the pinned file-attestation action. Budget `id-token: write`, `attestations: write`, `contents: read` and `actions: read`, with every other permission disabled. Actions read is only for authenticated archive metadata. No candidate checkout, scripts, cache, evaluated inputs, deployment environment, repository secrets, storage record or registry push in that job. Use a literal subject path and explicitly disable registry and storage publication. The signer accepts the positive artifact ID and SHA-256 digest only from the reviewed collector job’s pinned upload outputs. It fetches GitHub metadata by that exact ID using its scoped Actions read permission and verifies the same run ID, upload digest, literal `aitm-ci-collector-a<attempt>` name, nonexpiry, bounded size and digest. Download by validated ID with the pinned same-run downloader, no injected downloader token, `skip-decompress: true` and digest-mismatch set to error. Recompute the archive digest before extracting only a regular `candidate.json` of at most 1 MiB to a fixed empty temp directory. Reject wrong ID, name, attempt, links, traversal, duplicates or other archive members before signing. Only validated Actions/upload metadata selects the archive. A shared run namespace does not confer uploader authority. The expected-name upload fails on a collision, and no other job’s artifact is accepted in its place. Candidate fields never select paths, URLs, commands, environment or action arguments. Pass only the fixed validated bytes to the pinned signer. The canonical job succeeds only after successful complete collection, signing and upload.
- The final `aitm-ci-evidence-a<attempt>` archive contains the `aitm.ci-candidate/v2` JSON and a single Sigstore bundle for its exact bytes. The attempt archive, repository attestation record and append-only public Sigstore transparency entry are distinct. For this public repository the GitHub record and permanent public Rekor entry expose the signed subject digest and signing metadata, including repository, workflow path, merge ref/SHA, run ID and attempt, runner type and signing time. The SHA-256 subject binding is in the signed statement, and the workflow and attempt identity is in the certificate. Disabling registry and linked-artifact storage publication leaves the attestation and transparency publication in effect. Future authorization must explicitly cover the signing permissions, public subject digest and metadata for the one diagnostic and separately for recurring PR signing. Keep the subject sanitized and stop in Planning if either scope is absent. [GitHub attestation generation](https://docs.github.com/en/actions/concepts/security/artifact-attestations#how-github-generates-artifact-attestations). Verify all workflows and referenced controls eligible on the diagnostic PR, with only the reviewed diagnostic eligible for that proof. Keep trunk-push evidence separate. For a trunk push the merge-ref signing requirement does not apply, and it cannot satisfy a PR gate. Retain safe digest, verified claim summaries and archive provenance on planning.

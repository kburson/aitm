# #139 Classify the pytest inventory

[Accepted #133 design](../../133/design/test-impact-analysis-design.md#4-inventory-shards-and-test-evidence) · [Accepted T02](https://github.com/kburson/aitm/blob/dbe0d68b3e7b977c9fbf51e26d9ae8c6f629af84/.aitm/stories/001/133/plan/test-impact-analysis-implementation-plan.md#L187) · [Delivered #138 comparison](../../138/attachments/serial-baseline.md)

T02 turns a complete pytest collection into explicit execution obligations. It assigns a suite, owner, runner scope and isolation group to each exact pytest ID. This gives subsequent selection and shard assignment the same definition of the full applicable inventory. The existing #103 serial workflow remains the delivery gate.

## Contract

- `classify(collection, suite_policy) -> Inventory` is an offline projection. The caller supplies the collection and independently selects the intended workload in the reviewed suite policy with the applicable #103 policy bytes. Preserve the exact snapshot identity, source kind, collection receipt, observer, controls and runner identities, and the digests of both policy documents. A local observation binds the local content identity. A hosted input is a caller-verified `CollectionProof` that binds the exact tested tree and run attempt. The projection checks shape, completeness claims and internal consistency. T07/T08 own qualifying and authenticating hosted observation. There is no hosted TIA proof available at this leaf.
- An obligation is keyed by `(provider, owner, platform_scope, nodeid)`. Provider is pytest. Owner is the `aitm-usage` package or `ci-tools`. Preserve the full case-sensitive node ID and its parameter suffix, including punctuation, slashes and simulated platform names. Validate the repository-relative source part separately. Use the declared runner scope for each obligation, so the same exact ID can occur once in each required platform scope. Preserve owning profile, suite, isolation group, capability requirements, mandatory flag, allowed skip reason, required child labels and collection disposition on each row.
- The reviewed policy enumerates the exact required `(profile, platform_scope)` pairs for each workload. `full` requires both `product-cli` and `ci-helpers` on `darwin-apfs`. Match each pair to one collection component with the same repository, snapshot and source kind as the envelope. A successful full call returns one exact union with `scope_status=complete_workload`. T05 full fallback and T11 assignment use that complete inventory. T02 owns this projection and union only. T07/T08 supply qualified hosted inputs when available.
- `compare-product-base`, `compare-product-cli` and `compare-ci-helpers` are separate reviewed workloads, each with one profile on `darwin-apfs` and `scope_status=comparison_component`. A comparison component cannot satisfy full-workload admission. A historical #103 replay or advisory helper receipt cannot fill a qualified hosted component. Replay references are permitted only for comparison workloads and preserve their original provenance.
- Reject missing, extra or duplicate pairs, unavailable capabilities, incompatible component bindings, malformed or incomplete collection, deselection, unknown IDs, duplicate obligations, contradictory policy, unexpected skip/xfail declarations and missing mandatory IDs. Report one refusal. An optional skip requires the exact ID and reason from #103. Keep the ID in the inventory when that allowance is observed. Collection supplies no runtime outcome or coverage result. Those checks remain with #103 or the later qualified observer.
- Sort obligations and scope records deterministically and retain each component’s profile and receipt identity. Bind source provenance and both policy digests into canonical UTF-8 JSON. Two observations with the same node set and different source identity produce different inventory identities.

## Proposed suite and ownership rules

The file and exact-test rules below are the proposed T02 classification. Own-design acceptance approves this mapping. Unknown files require a reviewed explicit rule. Within a reviewed module, the module rule applies to parameterizations and other collected IDs unless a declared exact test-family override applies. Compare the function-qualified selector after isolating the parameter suffix. Preserve the unmodified ID in the obligation. An exact override replaces the module suite. Duplicate keys, two applicable override rules or an override outside a declared module are policy errors.

The installed CLI test belongs to the product-plus-CLI profile and carries mandatory child label `cli-help`. The one-shot test carries `service-one-shot` in that profile. The historical product-only base has the applicable product IDs, with no CLI test or child-proof expectation. The helper profile covers the four explicit workflow test targets, each represented, and has its own ownership and collection. Focused TIA tests are separately verified at delivery.

Read the six mandatory product cases, one optional skip and the required child labels from the applicable #103 policy. Validate the explicit child-to-test mapping against that label set. The current hosted profiles require Darwin/APFS. Mark the actual inherited ACL case with a native ACL obligation. Mark the real firmlink cases `test_install.py::test_backup_refuses_store_through_physical_path_alias`, `test_ledger.py::test_apfs_firmlink_overlap_refused_before_private_creation` and `test_ledger.py::test_distinct_apfs_alias_cannot_admit_a_second_writer` with explicit APFS obligations. Keep the optional install firmlink skip when the host lacks that alias. Tests simulating Linux, FreeBSD or Darwin in parameters keep their actual runner scope.

Put the three system rules in a single `system-process` isolation group. Put integration cases in `native-process-state` for `test_{activation_receipt,codex,export,host_fs_publication,host_fs_security,install,ledger,monitor_control,monitor_ledger_version,monitor_legacy,monitor_registry,monitor_scope,rollup,scopes,service}.py` to keep real host, writer, publication, monitor and process fixtures together conservatively. Use a module group for other integration modules and `ci-helper-serial` for the four helper targets. Unit cases use a pricing group. T11 can only split groups with separate isolation evidence.

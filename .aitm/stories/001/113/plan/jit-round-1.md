**Design.** Leave the v1 store initializer, identity/key derivation, legacy row shape and encoder intact. Admit v1 and v2 only when the declared SQLite version matches its exact schema and project/key identity. The v2 schema adds a separate append-only monitor revision table with the existing commit sequence and an explicitly versioned allowlisted payload. Keep legacy rows and checkpoints untouched, and read both views from one SQLite snapshot. Distinguish native surface, normalized observation time basis, usage availability, and optional provider cost evidence. Keep the legacy model and pricing codec unchanged. The first monitor codec covers Codex and Claude; M05 owns Grok and provider-specific cache and cost semantics.

**Migration and compatibility.** `Ledger.upgrade_monitor_schema(expected_sequence)` performs the DDL and version tag update in one guarded `BEGIN IMMEDIATE` transaction with the existing project writer lease, a rechecked expected sequence and a validated result. It neither increments the usage sequence nor rewrites v1 state. A stale handle refuses use after the version changes. The caller opens a fresh ledger with the returned identity. M03 exposes no migration command or production invocation. Backups retain exact v1 manifest bytes and select v2 only with a validated matching v2 store and payload. Refuse mixed schema bundles or cross-version legacy restore; M16 owns coordinated migration and rollback. The installer probe recognizes the exact v1 fingerprint from legacy wheels and both exact fingerprints for the new wheel. A v2 target requires v2 capability. Preserve all other runtime identity checks.

**CLI.** Distinguish global `--project STATE_DIR` as `legacy_state_dir` from `monitor report --project UUID` as `project_id`. Validate only the scope used by that handler and reject mixed forms. The monitor report route fails explicitly as unavailable and reads no ledger until the fenced report exists in M13. Legacy flags, invocations and output stay compatible.

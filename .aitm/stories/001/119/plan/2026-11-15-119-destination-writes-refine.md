## Existing implementation seams

- `RoutingJournal.as_of(sequence)` already reads and decodes exact claims, content revisions, disputes, dispositions and paired settlement, validating the source key and resuming from committed journal state. `PendingClaim` is a read model with key, owner, immutable captured provenance, typed usage and revision; incoming Python fields alone cannot authorize project writes. At JIT bind the exact stored canonical claim identity, destination and sequence to an issued commit operation and compare with the durable row. Preserve journal `as_of` committed-history semantics and use a separate delivery/ACK readback contract.
- `Ledger.writer` already holds the account-wide project guard, local lease, pinned directory/store and database identities. `Ledger._write_transaction` checks the writer, private key and exact DB identity under `BEGIN IMMEDIATE`. `upgrade_monitor_schema` and `monitor_as_of` already open the typed `monitor_revisions` structure with local source-reference validation. Reuse the authenticated codec and existing project-key pseudonyms. Preserve the legacy row shape and all existing legacy commands. Project monitor writes should have a distinct durable lineage binding and must not persist raw service provider names, raw prompt/path IDs or contain a cross-scope secret.
- A failure before destination commit retains the claim. A failure after destination commit but before ACK rereads the same verified destination receipt and cannot produce a second row. Rev 1 and successors require exact service key/project/lineage plus current project receipt binding. A stale ACK must never regress an accepted publication tail. A late conflict projects a dispute without a new project write. Registry and storage readback guard against foreign owner/receipt substitution; there is no inferred ownership from a destination key.
- Use a per-project unresolved capacity count deduplicated by service identity plus expected revision. Full destination refuses new pending obligations for that destination with an explicit held outcome, while genuine previously known replay/dispute still works. A batch with an unresolved active obligation keeps its shared cursor behind it. A different non-saturated destination and independent stream still progress under the same coordinator. No network, scheduler or production changes.
- Journal-only candidates are a distinct typed outcome. Authenticate exact stored identity and original journal sequence for both durable ownership/revision disagreement and the released source exclusion. There is no fabricated project write, scope membership, destination receipt or additive usage for a coverage candidate. Final publication only through #122.

## Findings

1. **CI1 is estimated exactly at the four-hour leaf cap, with no margin and the plan's most uncertain scope (plan lines 25, 29, 52; design line 54).** In one leaf, CI1 must deliver:
   - the first workflow, policy, two helpers, a standalone base observer with its own mid-leaf independent review and digest publication, a separate macOS base-baseline job, child-subprocess coverage shards, the wheel smoke, the aggregate and the evidence artifact channel;
   - controlled negative native proofs, then the bootstrap PR review and merge, the trunk push verification, a representative integration-target PR and a fresh-candidate-after-movement demonstration.
   
   This is the first-ever Actions route. Hosted behavior is unknown and each macOS attempt is forecast at up to 10 runner-minutes. Line 52 says "Include the base refresh, child coverage and artifact proofs in the four-hour forecast before starting. Replan or split if the forecast no longer fits." That defers the cap check to pickup, but the design asks refinement itself to produce estimates of at most four hours. A 4.0 h figure with no itemized breakdown does not show that the leaf fits.
   - Failure scenario: CI1 overruns partway through the bootstrap PR, after the workflow is open on a same-repo PR but before merge. The plan must then split mid-flight, with a partly reviewed gate-control change open and no leaf able to close on its own evidence.

2. **The integration-target route and the target-movement demonstration cannot be executed as written (plan line 52; design lines 23, 27, 50).** CI1 must "Verify … an ordinary PR into a representative CI-enabled integration branch" and "Demonstrate a fresh candidate after base or target movement". The plan does not say:
   - which integration branch to use, whether it already exists, or who creates or updates it with the verified workflow and policy (design line 27, "update any pre-existing intended integration parent");
   - what authorizes that outward branch and PR action, given the global constraint "Use only the named source story and its declared target" (line 19);
   - what the representative PR contains and how it is closed or disposed of;
   - how base or target movement is induced. Moving protected trunk needs some other authorized merge. Moving the integration branch needs an authorized push. The bootstrap PR is already merged by the time this step runs, so the design's `synchronize` or authorized-reopen route (line 23) must happen on some specific PR, and the plan does not name it.
   - Failure scenario: after the bootstrap merge, the implementer has no authorized integration branch and no sanctioned way to move a target. CI1 cannot reach its own closure proof (line 25) and stays open indefinitely, or the implementer improvises an unreviewed branch or push.

3. **CI2's closure needs a live "read-only case" that the plan never defines, so CI2 may not be closable on its own (plan lines 34, 60, 68, 72).** CI2 closes after it can "run the delivered trusted copy on a read-only case". The verifier works on a live open PR: it requires agreement between the live target tip and the live head. Once CI2's own PR merges, there may be no open source PR with an exact candidate until CI3 opens. CI2's closure would then wait on CI3, which breaks independent closability. Line 34 also promises that CI2 refuses stale or insufficient identity "from fixtures and a controlled live readback", but no step defines that controlled live readback: which PR, what state, and how stale state is produced safely.
   - Failure scenario: CI2 merges and the closure owner has nothing to run the trusted copy against. CI2 stays open until the CI3 PR exists, and the CI2 and CI3 closures, plus the parent comparison, collapse into one moment.

4. **The run-to-tested-merge binding probe comes last, even though it decides whether CI1 can continue at all (plan line 52; design lines 17, 19, 23).** Line 52 says "first establish that authenticated GitHub run/check metadata can bind the tested commit", but that sits in the final step, after the helpers, observer, wheel smoke, aggregate and artifact steps. For `pull_request` events, the workflow run's and check suite's `head_sha` are the PR head, not the test-merge commit. The PR's `merge_commit_sha` is mutable and is recomputed as the base moves. The plan names no specific API field expected to provide an independent binding from run to tested merge.
   - Failure scenario: most of the four-hour budget goes into building CI1. Only then does the first real run show that GitHub metadata cannot bind the tested merge without relying on candidate output. The plan's correct stop-and-replan route is triggered after nearly all of the effort is spent.

5. **CI1's helper tests do not include a failed required test outcome (plan line 45; design lines 44, 50).** The design's first required failure demonstration is "a failing test", and it requires every required ID to "meet its expected outcome". Line 45 lists zero tests, unexpected skips or xfails, missing or duplicate IDs and other cases, but no required ID with a `failed` call phase, a setup or teardown `error`, or a nonzero pytest exit while the other evidence files look complete. Line 49's aggregate fixtures cover a failed *job*, not a failed test outcome inside a job that `python_gate.py` evaluates.
   - Failure scenario: a workflow change swallows pytest's exit status, for example with `|| true` or `continue-on-error`. The outcomes file then records a failed required node ID, but no tested rule in `python_gate.py` refuses it, and the gate can pass.

6. **CI2's fixture list leaves out refusal cases the design names (plan line 58; design lines 19, 51).** The design requires each expected job to "appear exactly once and succeed", and it lists "neutral, missing, ambiguous or partial-rerun evidence". It also requires the PR's live head to match the event head and the second parent, and candidate-reported identities to match GitHub. Line 58 has neutral or cancelled jobs, duplicates and partial reruns, but it lacks:
   - (a) a *missing* required job and a *skipped* required job;
   - (b) a live PR head that moved without a new event, as distinct from "branch ref advanced", which reads as the target;
   - (c) a candidate record whose reported head, base or tested identity disagrees with the GitHub metadata.
   
   Line 59 says "compare candidate-reported identities with it" but sets no fixture obligation.
   - Failure scenario: a verifier that only checks the `conclusion` of jobs that are present accepts an attempt where a required lane never ran. Or it accepts a candidate record that names a different tested commit. All listed fixtures still pass.

7. **The aggregate predicate exists in two copies, and only one is tested (plan line 49).** "Define the same shipped aggregate predicate in `python_gate.py` and the workflow" creates two copies. The behavioral fixtures ("Use the actual shipped predicate for these cases") can only exercise the Python copy. The workflow-side `if:`/`needs` logic is then covered by a single native failing and corrected rerun.
   - Failure scenario: the workflow expression treats `skipped` as acceptable, or a later edit drops a lane from `needs`. The Python fixtures stay green, `aitm-ci` reports success for a run with a skipped required lane, and the closure owner reads a green aggregate.

8. **Some design items are missing from the plan (design lines 25, 33, 42, 44).** Each is small, but together they are traceability gaps:
   - (a) the design asks to "report branch coverage separately where supported", and the plan never mentions branch coverage;
   - (b) the design asks for a Ruff "lint and formatting check", and line 49 says only "Run Ruff";
   - (c) dependency caches "keyed by OS, runtime and lockfile";
   - (d) "a separate workflow-and-ref group for pushes" alongside the per-PR concurrency, and preserving cancelled outcomes;
   - (e) recording queue, setup, test and total elapsed time separately for cold and warm runs. Line 16 says only "cold/warm timings", and no CI1 step or `candidate.json` field records them.
   - Failure scenario: CI1 ships without format checking or a push concurrency group, and the reviewer cannot trace that back to a plan step.

9. **The helper denominator, helper environment and file ownership are not fully defined (plan lines 41, 46–47).** Line 47 says "Use explicit production inputs for both denominators", but the plan does not name the helper files that count toward the 90% helper floor: `python_gate.py`, `pytest_evidence.py`, and later `verify_pr.py` and `file_checks.py`. It also gives no test owner for `pytest_evidence.py`; only `test_python_gate.py` is listed. Neither `tools/ci/` nor CI2 has a project or lock of its own, so it is unclear which locked environment runs the helpers and their pytest-cov tests. Finally, the new `aitm-usage --help` child test with "an observable help-output assertion" (line 46) has no owning test file. The Owns list (line 41) covers only the scoped instrumentation in `test_service.py`.
   - Failure scenario: `pytest_evidence.py` is left out of the helper denominator, or it is included with no tests. The helper floor is then either silently narrowed, or it fails late on a file with no planned test owner.

10. **The identity of the base observer is ambiguous (plan lines 44, 46).** Line 44 describes a "standalone pytest evidence observer" for the base. It must use only the base's locked pytest and the standard library, run outside both checkouts, and take "no candidate checkout or imports". Line 46 says "the pytest evidence hook records the two named child invocations, exits and PIDs", which depends on candidate test instrumentation in `test_service.py`. The plan does not say whether the observer and `tools/ci/pytest_evidence.py` are the same blob. That matters for line 44's "Subsequent base runs use the delivered observer".
    - Failure scenario: the reviewed and digest-pinned observer turns out to differ from the delivered hook. Later base runs then use an unreviewed blob. Or the single hook's child-tracking code expects instrumentation the base tree doesn't have, and the base run errors.

11. **The hosted-minute forecast leaves out the separate macOS base job (plan lines 18, 44).** Line 18 bases the "10 hosted runner-minutes per full macOS attempt" on the local suite plus setup. Line 44 adds a full serial baseline run on the event base, in its own clean hosted macOS workspace, for every PR candidate. That roughly doubles macOS suite time per attempt. The controlled negative native proofs also add attempts.
    - Failure scenario: the cost and queue-time forecast for each pickup is understated by about half, so line 29's refinement trigger fires late.

Name the PR used for the representative and movement proofs, its content and its disposal. State the authorized way to induce base or target movement: the `synchronize` update path or an authorized reopen, on a named PR. Add any new outward action to the Before Develop checklist record.
3. For Finding 3, define the concrete read-only live case CI2 uses after its own merge, so that CI2 closes without waiting for CI3. Also define the "controlled live readback" refusal promised on line 34, or remove that promise and rely on fixtures. Examples include a named reviewed no-op PR kept open against the trusted target, or verifying CI2's own PR before merge with a trusted-copy check run from the target after delivery.

Name the GitHub API fields expected to bind the run to the tested merge, such as run `pull_requests[].head/base.sha`, `head_sha`, PR `merge_commit_sha` and check-suite fields, along with the stop criterion.

6. For Finding 6, add CI2 fixtures for a missing required job, a skipped required job, a live PR head moved without a new event, and a candidate-reported head, base or tested identity that mismatches GitHub metadata.
7. For Finding 7, give the aggregate predicate a single source, for example by passing `toJSON(needs)` to the `python_gate.py` predicate from the aggregate job. Otherwise, add tests that exercise the workflow-side expression itself against the same failed, missing, skipped and cancelled cases.

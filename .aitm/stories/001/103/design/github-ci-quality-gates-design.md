# GitHub CI and repository quality gates

Draft for design review. The owner asked for a GitHub Actions build, Python and TypeScript quality checks, document and structured-file linting, and a test runner that can scale. The owner set a 90% coverage floor and considers 100% worthwhile where meaningful behavioral tests reach it. The tool choices and rollout below are proposals.

## Outcome and boundaries

Give every source story PR timely, reproducible test and quality evidence on its exact candidate so independent review and story closure can follow without waiting for an epic release. Build the first lane against the repository's current code. Make it possible to add future packages without replacing the evidence model.

The current trunk contains one Python package, `aitm-usage`, with a `uv.lock`, Ruff and pytest. It has no TypeScript package. At intake, GitHub Actions was enabled and reported zero workflows. The [#102 compatibility report](../../102/attachments/report.md) demonstrates macOS dependencies in private paths and exclusive publication. Use hosted macOS for the required collector suite and wheel smoke. Linux can run portable lint and document checks. A hosted CI pass is source validation. Actual provider, GUI LaunchAgent and deployment qualification remain separate operational evidence.

This PBI owns general PR CI. Core C59 and C69 own their existing wheel and release qualification contracts. TypeScript application code, Linux collector porting, release publishing, production activation and starting Core are outside the PBI.

## Workflow and evidence

Add `.github/workflows/ci.yml` through the normal protected PR path. Run the full applicable checks on ordinary PRs into source branches, including declared epic integration targets, and on pushes to trunk. Use a single stable result name, `aitm-ci`, which depends on all validation jobs. Have the aggregator inspect required job results even when a dependency fails or is skipped. A missing, cancelled or skipped required lane, or a cancelled run without an aggregate result, cannot produce a passing gate. Detect supported packages explicitly. A known required package disappearing fails the gate. An absent optional language is recorded as not applicable. The first source PR must demonstrate that the workflow runs on the intended target. A workflow-wide path filter must not strand or silently bypass a required check.

Retain exact PR head SHA, base SHA, tested commit and per-job outcomes. If GitHub checks out a test merge, record and verify its two parents against the event head and base. A changed candidate needs a fresh applicable result. Independent agent review stays a separate gate. Use read-only permissions, hosted disposable runners, pinned action revisions and tool versions, and dependency caches keyed by OS, runtime and lockfile. PR jobs use fixtures and require neither production credentials nor access to an operator's machine. Cancel superseded runs for the same PR while preserving their actual cancelled disposition. [GitHub workflow events](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows) · [GitHub required checks](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks)

At first pickup, record the exact bootstrap route in the manual checklist. The repository cannot already show a passing CI check before its first workflow exists. If the checklist requires a scoped authorization for that preflight gap, record it before Develop. The bootstrap PR still needs a real Actions result and independent review, including the coverage floor. Decide enforcement of the stable check in a separate explicit ruleset action after verifying its results and intended targets. Retain the observed check names and results for the closure owner. [Manual delivery checklist](../../../../manual-delivery-checklist.md)

## Tool choices

| Surface | Proposed check |
| --- | --- |
| Python | Use the existing uv lock, Ruff lint and formatting check, and pytest. Build one wheel from the verified candidate using a pinned interpreter and build backend. Install that exact wheel in an isolated environment and run the CLI smoke. Keep its digest. |
| TypeScript | When a real package exists, run lockfile-based install, ESLint with typescript-eslint, `tsc --noEmit`, and Vitest. Document the lane and its contract now. Activate it with the first package and report missing configuration as a failure if TypeScript project files are present. |
| Markdown | Use markdownlint-cli2 with a pinned version and a reviewed rule set. Gate tracked maintained docs in the checked-out source tree. If the rollout finds existing violations, review targeted fixes or a named baseline rather than reformatting historical evidence. |
| JSON and YAML | Parse tracked JSON strictly and fail on invalid syntax or duplicate keys. Validate against declared schemas where they exist. Use yamllint for YAML and actionlint for GitHub Actions semantics. Keep YAML boolean rules compatible with Actions' `on` key. |

Use the same commands locally and in CI. Pin tooling and locks. Publish a short command reference and define the checked file sets, including how vendored, generated and immutable historical material is handled. The initial PR gate covers source refs. Planning is a separate branch with its own documentation history and direct publication route. Any later planning-branch workflow should validate its named tree and use a reviewed baseline for preserved artifacts. [uv](https://docs.astral.sh/uv/guides/integration/github/) · [Ruff](https://docs.astral.sh/ruff/) · [ESLint](https://eslint.org/docs/latest/use/configure/configuration-files) · [typescript-eslint](https://typescript-eslint.io/getting-started/typed-linting/) · [markdownlint-cli2](https://github.com/DavidAnson/markdownlint-cli2) · [yamllint](https://yamllint.readthedocs.io/en/stable/) · [actionlint](https://github.com/rhysd/actionlint)

## Coverage and test scaling

- Gate line coverage at **90% per active product package**, including unimported production modules. For Python use pytest-cov and coverage.py, and configure subprocess measurement for the CLI and process tests where their exit mode can produce usable coverage. For TypeScript use Vitest's V8 coverage when the lane activates. Report branch coverage separately where supported. Add an explicit, reviewed justification for any exclusions. Preserve the actual baseline and the scope of the measurement.
- Make **100% aspirational** where meaningful tests reach it. Cover user-observable behavior, failure and recovery, and important invariants. Treat a below-floor baseline as a real gap. The first gated delivery must meet 90%. Add behavior tests for genuine gaps within the leaf's budget, or replan and split out a prerequisite that brings the baseline to the floor. Check covered versus executable line counts before display rounding.
- Start with the full required macOS suite serially. Emit JUnit, coverage and slow-test durations tied to the same candidate. Name required cases and any permitted platform capability skips in the reviewed validation scope. For example, the existing APFS firmlink case can be capability-dependent, while a skip because the package is missing indicates a broken lane. An unexpected skip or an unexercised required case keeps the gate closed. Correct the runner or use an explicitly authorized disposition for the affected capability. Run independent lint and test lanes concurrently, and cache dependencies. Establish a repeatable runtime and test inventory before attempting test sharding.
- As runtime grows, use pytest-xdist for groups proven safe to parallelize. Keep host-sensitive, process, lease or shared-state tests serial until isolation is demonstrated. Vitest can shard by test file when its lane grows. Compare collected and executed IDs with a complete baseline. Detect missing and duplicate shards, merge coverage from the same candidate and scope, and evaluate the 90% gate on the combined result. An incomplete or mismatched report cannot satisfy the check. Optional changed-test runs may give early feedback. Required CI keeps the complete applicable suite. [pytest-xdist distribution](https://pytest-xdist.readthedocs.io/en/stable/distribution.html) · [pytest-cov](https://pytest-cov.readthedocs.io/en/stable/config.html) · [Subprocess measurement](https://pytest-cov.readthedocs.io/en/stable/subprocess-support.html) · [Vitest sharding](https://vitest.dev/guide/cli.html#shard) · [Vitest coverage](https://vitest.dev/config/coverage.html)

## Acceptance for the first delivery

1. A real PR records its head/base and checked commit. A successful run produces the stable result, locked Python lint and full supported-host tests, the exact wheel smoke, quality checks for the declared Markdown/JSON/YAML files, and named CI evidence the manual checklist can use.
2. A deliberately failing test or malformed configuration, a below-90% coverage result, an unexpected or required-case skip, and a missing or cancelled required job each prevent a passing gate. An absent TypeScript product package is reported as not applicable. The future TypeScript command contract is documented.
3. Record the initial product coverage baseline, test inventory and timings. Verify that expected subprocess coverage is included when available and confirm the installed wheel smoke uses the candidate artifact. Required coverage is based on behavioral tests, with no narrowing of production scope to reach the number.
4. Record the review and merge using the story checklist and close the story when its own last gate passes. Any expanded scope, including work needed to bring the baseline to 90%, is estimated at refinement. Split the PBI if it exceeds the normal four-agent-hour leaf limit.

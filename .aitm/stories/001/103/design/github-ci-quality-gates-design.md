# GitHub CI and repository quality gates

Draft for design review. The owner asked for a GitHub Actions build, Python and TypeScript quality checks, document and structured-file linting, and a test runner that can scale. The owner set a 90% coverage floor and considers 100% worthwhile where meaningful behavioral tests reach it. The tool choices and rollout below are proposals.

## Outcome and boundaries

Give every source story PR timely, reproducible test and quality evidence on its exact candidate so independent review and story closure can follow without waiting for an epic release. Build the first lane against the repository's current code. Make it possible to add future packages without replacing the evidence model.

The current trunk contains one Python package, `aitm-usage`, with a `uv.lock`, Ruff and pytest. It has no TypeScript package. At intake, GitHub Actions was enabled and reported zero workflows. The [#102 compatibility report](../../102/attachments/report.md) demonstrates macOS dependencies in private paths and exclusive publication. Use hosted macOS for the required collector suite and wheel smoke. Linux can run portable lint and document checks. A hosted CI pass is source validation. Actual provider, GUI LaunchAgent and deployment qualification remain separate operational evidence.

This PBI owns general PR CI. Core C59 and C69 own their existing wheel and release qualification contracts. TypeScript application code, Linux collector porting, release publishing, production activation and starting Core are outside the PBI.

## Workflow and evidence

Add `.github/workflows/ci.yml` through the normal protected PR path. Run the full applicable checks on ordinary PRs into source branches, including declared epic integration targets, and on pushes to trunk. Subscribe to ordinary `pull_request` activity on all branches without workflow-level branch or path filters. For a declared source target, absence of the canonical check leaves its gate open. Use a single stable result name, `aitm-ci`, which depends on all validation jobs. Have the aggregator inspect required job results even when a dependency fails or is skipped. A missing, cancelled or skipped required lane, or a cancelled run without an aggregate result, cannot produce a passing gate. Detect supported packages explicitly. A known required package disappearing fails the gate. An absent optional language is recorded as not applicable. The first source PR must demonstrate that the workflow runs on the intended target. A workflow-wide path filter must not strand or silently bypass a required check.

Bind each passing result to the repository and canonical workflow path and ID, PR number and event, declared target, run ID and attempt, exact head and base SHAs, tested commit, gate-defining blob IDs and per-job results. Require a completed successful attempt of every applicable job and its own `aitm-ci` result. Check-source enforcement, if later enabled, should bind the expected Actions app where supported. Apply the workflow and run binding independently of the merge UI.

Use `tools/ci/verify_pr.py` as a read-only closure-owner command. Run the trusted verifier from the current protected target checkout, outside candidate execution. It reads authenticated, read-only GitHub metadata for the PR, canonical workflow, workflow run, check suite and attempt-specific jobs. Read the declared target's live branch ref directly. The live tip, event base and raw test-merge first parent must agree. The PR's live head must agree with the event head and second parent. Bind the tested commit to the selected run through GitHub's metadata and inspect its raw commit object. The sanitized candidate record supplies lane outputs, including inventory, coverage counts and digests. It cannot supply trusted identity. Any identity mismatch or missing provider linkage, including a fork run without sufficient PR evidence, holds the gate. Choose the newest canonical PR run with the exact live repository, PR, target, head and base, then require its latest attempt to be complete and successful. Order matching runs by creation time and run ID. A newer failed or pending matching run holds the gate. Older legitimate runs are history. Multiple aggregate jobs within the chosen attempt are ambiguous. Require each expected job to appear exactly once and succeed in that same attempt, so a partial rerun that reuses earlier jobs cannot satisfy it. The verifier outputs a dated evidence result with exact identities, observed verdict and any blocking reason. Cover the selection and refusal behavior with recorded API fixtures and apply a separate 90% line floor to first-party executable CI policy helpers.

Before review and again before merge, the closure owner runs that verifier and compares the trusted base and candidate gate-defining paths. Record exact blob IDs for the canonical workflow, verification and lane helpers, coverage policy and roots, exclusions and required package/test inventories, tooling locks, lint rules and collection settings. Changes to those controls require explicit owner disposition and independent review of their effect. The 90% floor remains fixed. Candidate output alone cannot approve changes to the controls that produced it. At first bootstrap apply the same evidence and diff procedure manually using the approved design and exact GitHub metadata, until the verifier's own delivery is verified. Introduce the verifier through separately reviewed delivery and use it from a trusted target revision after that. The parent acceptance compares the manual and trusted verifier results on an exact candidate both can check.

For a PR, validate the raw test-merge commit object has the event base and head as its two parents in that order. A moved base, retargeted PR or changed head needs a fresh event and fresh applicable evidence. Subscribe to `opened`, `synchronize` and `reopened`. For retargeting or base movement without a fresh event, update the story branch against the declared target through its normal allowed update path and push to trigger `synchronize`. If the branch already includes the target and no head update is needed, use an authorized reopen of the same PR to get a fresh event. Title and description edits create no CI runs. A rerun retains its original event SHA and ref. A trunk push check validates its own tree. [GitHub workflow events](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#pull_request) · [GitHub reruns](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/re-run-workflows-and-jobs) · [GitHub required checks](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks)

Use ordinary `pull_request`, read-only permissions, hosted disposable runners, pinned action revisions and tool versions, and dependency caches keyed by OS, runtime and lockfile. Keep checkout credentials disabled and PR jobs fixture-only, with no production secrets, deployment rights or access to an operator's machine. Handle fork runs through ordinary GitHub approval and read-only controls. Key concurrency by workflow and PR number, with a separate workflow-and-ref group for pushes. Superseded candidate runs may cancel. Preserve their cancelled outcome.

Before Develop, record the exact bootstrap route in the manual checklist. Its preflight gap is the absence of an existing proven route. Record any required authorization for that specific gap. A same-repository bootstrap PR can run the proposed `pull_request` workflow. It still needs a real passing Actions result, measured coverage of at least 90% and independent review before merging. After merge verify the actual trunk push result, update any pre-existing intended integration parent with the verified workflow and policy, and exercise a representative PR into that parent before declaring the route ready. A declared target without a verified canonical result stays blocked. Decide enforcement in a separately authorized ruleset action once actual results and targets are known. ## Tool choices

| Surface | Proposed check |
| --- | --- |
| Python | Use the existing uv lock, Ruff lint and formatting check, and pytest. Build one wheel from the verified candidate using a pinned interpreter and build backend. Prepare locked runtime dependencies in a clean environment that excludes the editable project, verify the built artifact's SHA-256 immediately before install, then install that exact wheel with `--no-deps` and run the CLI smoke. Verify the installed command and import resolve inside that environment and retain the digest. |
| TypeScript | When a real package exists, run lockfile-based install, ESLint with typescript-eslint, `tsc --noEmit`, and Vitest. Document the lane and its contract now. Activate it with the first package and report missing configuration as a failure if TypeScript project files are present. |
| Markdown | Use markdownlint-cli2 with a pinned version and a reviewed rule set. Gate tracked maintained docs in the checked-out source tree. Measure the existing baseline before choosing a rule set. |
| JSON and YAML | Parse tracked maintained JSON strictly and fail on invalid syntax or duplicate keys. Exact test fixtures deliberately containing malformed syntax or duplicate keys may be excluded through a reviewed, reasoned path entry. Validate against declared schemas where they exist. Use yamllint for YAML and actionlint for GitHub Actions semantics. Keep YAML boolean rules compatible with Actions' `on` key. |

Use the same commands locally and in CI. Pin tooling and locks. Define the checked file sets in the reviewed policy, including exact justified fixture, vendored, generated or immutable-history exclusions. Measure existing Ruff, Markdown, JSON and YAML results on the exact base. Handle existing violations with targeted reviewed changes or an explicit named baseline. Keep repo-wide cleanup separately scoped. The initial PR gate covers source refs. Planning is a separate branch with its own documentation history and direct publication route. Any later planning-branch workflow should validate its named tree and use a reviewed baseline for preserved artifacts. [uv](https://docs.astral.sh/uv/guides/integration/github/) · [Ruff](https://docs.astral.sh/ruff/) · [ESLint](https://eslint.org/docs/latest/use/configure/configuration-files) · [typescript-eslint](https://typescript-eslint.io/getting-started/typed-linting/) · [markdownlint-cli2](https://github.com/DavidAnson/markdownlint-cli2) · [yamllint](https://yamllint.readthedocs.io/en/stable/) · [actionlint](https://github.com/rhysd/actionlint)

## Coverage and test scaling

- Gate line coverage at **90% per active product package**, including unimported production modules. Declare source roots, required test groups, exclusions and threshold in reviewed `tools/ci/policy.json`. For Python use pytest-cov and coverage.py. Verify collected data from the ordinary console CLI and normally exiting service fixture subprocesses. A missing expected child record is a verification gap. Deliberate hard-kill tests can validate recovery while their unflushed lines remain uncovered. The isolated wheel smoke verifies artifact behavior separately. For TypeScript use Vitest's V8 coverage when the lane activates. Report branch coverage separately where supported. Add an explicit, reviewed justification for any exclusions. Preserve the actual baseline and the scope of the measurement.
- Make **100% aspirational** where meaningful tests reach it. Cover user-observable behavior, failure and recovery, and important invariants. Treat a below-floor baseline as a real gap. The first gated delivery must meet 90%. Add behavior tests for genuine gaps within the leaf's budget, or replan and split out a prerequisite that brings the baseline to the floor. Compare raw covered and executable counts with integer arithmetic. Exercise 89.5% refusal and exact 90% success.
- Start with the full required macOS suite serially. Emit JUnit, coverage and slow-test durations tied to the same candidate. Record queue, setup, test and total elapsed time separately when comparing cold and warm runs. Name required cases and any permitted platform capability skips in the reviewed validation scope. For example, the existing APFS firmlink case can be capability-dependent, while a skip because the package is missing indicates a broken lane. Pin the runner label and record the capabilities required for the ACL, exclusive publication, writer lease and restart proofs. An unexpected skip or an unexercised required case keeps `aitm-ci` blocked even when the other lanes pass. Correct the runner and rerun the required cases. A separate policy disposition records the gap and carries no passing CI result. Run independent lint and test lanes concurrently, and cache dependencies. For the serial baseline as well as shards, compare candidate collection with the union of candidate executed and explicitly classified test outcomes. Every required ID must run once and meet its expected outcome. Compare against the exact base inventory and outcomes from trusted retained evidence or a controlled baseline run. Surface removed, deselected, newly skipped and newly xfailed IDs. A missing named required case holds the gate. Record explicit review of intentional inventory changes. Establish a repeatable runtime and inventory before sharding.
- As runtime grows, use pytest-xdist for groups proven safe to parallelize. Keep host-sensitive, process, lease or shared-state tests serial until isolation is demonstrated. Vitest can shard by test file when its lane grows. Apply the same inventory checks after distributing the suite. Detect missing and duplicate shards, merge coverage from the same candidate and scope, and evaluate the 90% gate on the combined result. An incomplete or mismatched report cannot satisfy the check. Optional changed-test runs may give early feedback. Required CI keeps the complete applicable suite. [pytest-xdist distribution](https://pytest-xdist.readthedocs.io/en/stable/distribution.html) · [pytest-cov](https://pytest-cov.readthedocs.io/en/stable/config.html) · [Subprocess measurement](https://pytest-cov.readthedocs.io/en/stable/subprocess-support.html) · [Vitest sharding](https://vitest.dev/guide/cli.html#shard) · [Vitest coverage](https://vitest.dev/config/coverage.html)

## Delivery order and acceptance

1. **Behavior coverage prerequisite, only if the baseline is below 90%.** Identify behavioral gaps and refine the smallest scoped tests that can reach the fixed floor. Establish a viable explicitly reviewed bootstrap test route before that prerequisite enters Develop. A partial baseline cannot greenlight the workflow bootstrap or #103. If no safe prerequisite route exists, return to planning.
2. **Bootstrap workflow and Python validation.** Use the documented manual evidence procedure for the bootstrap PR and any source leaf delivered before the verifier. Prove a real exact passing Actions run with at least 90% line coverage, required macOS tests, the locked wheel smoke, stable aggregate, and independent review. Demonstrate failure on a failing test, 89.5%, a missing or unexpectedly skipped required case, unavailable required Darwin capability and failed, missing, skipped or cancelled required job. Verify delivery to trunk and verify the actual trunk push result plus a representative integration-target PR and fresh run after base or target movement. This leaf closes on its own evidence and sign-off. The verifier is a subsequent leaf.
3. **Read-only PR evidence verifier.** Use the proven bootstrap route for its source PR, with manual readback until the trusted verifier is delivered. Independently review its source and 90%-covered behavioral tests. Exercise authentic metadata fixtures for wrong workflow, stale live base without a fresh PR event, absent fork identity, invalid merge parents, neutral, missing, ambiguous or partial-rerun evidence, and an undisposed gate-defining change. Verify its own delivery and close it at its own last gate.
4. **File quality and future TypeScript contract.** Extend the established workflow with tracked maintained Markdown, JSON, YAML and Actions checks. Demonstrate each applicable failure on a safe fixture, and demonstrate exact reviewed exemptions. Document the future TypeScript checks and visibly report the absent product package. Verify its own delivery and close it at its own last gate.

The parent compares the trusted verifier with manual readback for a named exact PR candidate after delivery and records the aggregate outcome. Each leaf follows the story checklist and its own last passing gate. Refine into estimates of no more than four agent-hours per leaf, with a split for any larger or newly discovered requirement. Runner label, image, Xcode or command-line tooling version, and projected hosted minutes belong in refinement and pickup evidence.

## Qualification question and prerequisites

Can an independent observer establish complete collection before assignment and actual execution afterward, on the same exact candidate, in both full and selected modes? Candidate Python, its pytest process and candidate-writable output are outside the trusted observation boundary. The controller and observer need an independently controlled principal, with protected invocation, expected obligations, receipt creation, authentication and custody. The authority must bind evidence of actual runner activity to the exact candidate, policy and assignments. A correctly shaped receipt, authenticated upload, matching digest, clean exit or consistent in-process report can establish properties of a report. Test collection and execution still require independent observation. Record any remaining influence that candidate code has over the meaning or completeness of the observations. [Accepted #133 design, §4](../../133/design/test-impact-analysis-design.md#4-inventory-shards-and-test-evidence)

Before any future trial, identify a pre-existing, explicitly authorized and isolated macOS/APFS runner and confirm the observer can operate outside the candidate's control. Use disposable, non-sensitive fixtures with independently declared expected IDs and outcomes, including a native child-process case. The trial needs a pinned capability receipt for the runner, OS/filesystem, exact source/tree, toolchain/lock, controls, principal and evidence channel. Bind observed trial results to the run/attempt and, for execution, to the prior collection and exact assignment. This intake established the historical #103 runner baseline. The authorized isolated runner and independent observer capability remain unverified for T07. Existing shared CI, production credentials and new repositories are outside this trial scope.

## Evidence the bounded trial would need

The cases below specify evidence and expected disposition for authorized fixtures. Run coverage and the actual observations would be recorded in the spike report.

| Case | Required evidence or refusal |
| --- | --- |
| Known-good collection and execution | An independent observation establishes the exact applicable IDs before assignment. It then accounts for the actual assigned IDs and outcomes in each mode. A selected run still depends on a complete pre-assignment inventory. |
| Receipt with expected shape and untrusted origin | The independent authority refuses the receipt as proof of collection or execution and records the reason. |
| Incomplete collection, including omission of a newly collected ID | Establish the independently expected complete set or refuse before assignment, even if the earlier base inventory still matches. Apply the same rule to full and selected modes. |
| Claimed pass without independent outcome evidence | Require observation tied to actual execution of the assigned ID. Refuse substituted or unverifiable results in either mode, including when in-process output appears successful. |
| Authenticated test failure with a missing sibling shard | Preserve the verified failure and separately record the missing evidence. Refuse an aggregate pass and retain the reason for each disposition. |
| Native child-process evidence | Bind independently observed child activity and required coverage to the fixture obligation and run. Missing or unverifiable child evidence prevents qualification for that scope. |

The spike deliverables are a sanitized qualification report, the pinned capability receipt if available, fixture dispositions with observed and missing evidence recorded, and either a bounded controller recommendation or a documented refusal. Qualification requires evidence for both collection and execution in both modes. Refuse when the independent principal or evidence channel cannot be established, when collection completeness or execution cannot be verified, or when the required capability and binding are missing. A full run must establish its own trusted evidence. Preserve a verified failure even when other evidence is unavailable. A refusal leaves #145/T08, #146/T09 and dependent work blocked on this capability and returns the boundary to #133 design review. Existing #103 gate authority and local advisory operation remain available.

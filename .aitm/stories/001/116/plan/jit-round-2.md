## Private registry and ownership

Reuse the platform ACL, pinned-directory, identity and guarded lease primitives in `host_fs.py` and `ledger.py`. Use an account-private monitor root outside checkout, separate from individual project stores. All mutable registry and applied command receipts use a single durable transaction under one account coordinator lease. Expose that lease for the later journal and coordinator to reuse. Validate root ownership, physical identity, private mode and pinned path at every read/write, including recovery. Readers open and validate one committed registry snapshot without taking the coordinator lease. They can read while the writer runs and never create the monitor root. An absent root means not adopted for legacy admission or unavailable for command status. Corrupt or substituted private state fails closed. No production service, migration or capture starts here.

`Registry.register_project(ProjectRegistrationRequest) -> RegisteredProject` uses an immutable project UUID and pinned private project state identity. Multiple physically distinct anchors can identify the same project. Resolve physical identity and ancestry before accepting owner-supplied anchors. Identical and nested anchors across different projects fail in either direction, including aliases. Refuse a changed inode or key at an adopted state path. Names, remotes and optional default driver are metadata and may change without creating a new project or changing its capture epochs. Source approval records an immutable source ID, exact installed provider/surface tuple and approved physical root. Projects enable separate edges to shared installations. A root, candidate file or configured path alone cannot establish project attribution or qualify an unproven provider version. The service consumes the registry view and performs discovery once per approved installation. Keep raw configuration paths private and out of CLI output, public receipts and export.

The private registry distinguishes proposed registration from an adopted existing ledger. M16 owns actual adoption/cutover. Legacy `register` and `source add-anchor` check the adopted state before any mutation or writer-lock attempt and return the exact `project-adopted-use-monitor` reason when the registry pins that identity. Recheck registration while holding its existing project writer guard. ## Capture epoch and command contract

`Registry.set_permission(CaptureChange, VerifiedBoundary) -> CaptureEpoch` applies one native stream boundary to one project/source edge under the coordinator. Persist monotonically ordered, service-keyed boundaries, generation and permission state for each stream. The coordinator applies a source-wide command atomically to its known stream boundaries and keeps it queued while required proof is unavailable. New streams enroll only after a verified starting boundary while permission is enabled. Exact boundary retries preserve one decision and stale or contradictory boundary input fails closed. The writer obtains `VerifiedBoundary` only from its source verifier against an exact M04-adapter-produced native boundary or observation and the pinned approved source and stream. The writer validates the service reference namespace and rejects stale, forged, misbound or caller-constructed proof. No command or CLI decoder can instantiate a trusted boundary. Tests use an actual adapter fixture through the production verification seam. Later scope resolution retains its own authority.

Evaluate eligibility from the original native span, not arrival or replay time. Use half-open permission intervals. A span wholly in an admitted epoch remains eligible for settlement from already-staged authorized evidence even if its revision arrives after disable. An unsplittable span crossing an enable or disable fence is a gap. A span in a disabled interval stays excluded after re-enable. Match stable source identity and native stream on every read. A revoked or no-longer-pinned root yields no new reads to repair a revision, even when already-staged authorized proof can settle. Later scheduler and routing owners call this registry seam.

`ControlInbox.enqueue(ControlCommand) -> ControlReceipt` uses a stable UUID and versioned typed, canonical owner-authorized envelope. Use private immutable atomic publication for queued bytes under an inbox publication lock separate from the coordinator lease. Expose both locks for M16. Writers acquire coordinator first and publication second. M16 also acquires the original project guard before freezing the applicable inboxes. Enqueue takes only the publication lock and reads a committed registry snapshot without acquiring the coordinator. Under that lock, check both the queued bytes and the durable receipt's canonical payload digest before a retry can publish. Reusing a UUID for different payload is a conflict. Concurrent exact retries converge to one receipt, and submission can never claim application. The single monitor writer calls `Registry.apply_pending(inbox, writer_lease, boundary_verifier)` under its coordinator lease. The method validates, applies and records the outcome and canonical payload digest in the same registry transaction, then cleans the exact queue entry while holding the publication lock. A crash after durable application and before cleanup replays without duplicate effects. An exact retry after cleanup returns the original outcome, and conflicting reuse still fails. Bootstrap calls this same writer entry point and command contract. The new CLI commands only enqueue or read status. Status prefers a durable receipt over queued bytes and rereads the committed receipt if the queue entry disappears during lookup. Path inputs are never copied to status output.

Extend `cli.py` with `monitor project register --config FILE`, `monitor source approve --config FILE`, `monitor project anchor add --project UUID --config FILE`, `monitor capture enable|disable --project UUID --source ID`, and `monitor command status --id ID`. Preserve existing global legacy state-directory versus monitor UUID parsing. Use explicit private config for owner declarations and stable caller-provided request IDs where supplied. For capture commands allow an optional request ID to retry across process boundaries and return the chosen stable ID. Use sanitized queued/applied/rejected status and a distinct unavailable command result. Tests exercise actual CLI parsing and queue persistence as well as direct registry operations. The startup service, runtime application loop and production adoption stay with their accepted later leaves.

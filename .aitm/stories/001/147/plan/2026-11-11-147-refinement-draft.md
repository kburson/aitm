## Proposed scope and invariants

Use the accepted interfaces in `tools/ci/tia/controls.py` and put focused verification in `tools/ci/tests/test_tia_controls.py`. Keep existing workflow, verifier, snapshot, classifier and policies as read-only inputs. The pinned #103 helper lane and #139 complete workload explicitly enumerate their existing targets. Run the focused T10 tests separately, following #139's verified delivery precedent.

### `qualify_controls(base, candidate, approvals) -> ControlDisposition`

- Derive the control diff from the exact verified endpoints using the control classification from trusted policy. Preserve the pinned #103 control coverage and the accepted #133 categories for selector, classification, discovery, coverage, workflow, verification and merge policy. Compare both old and new path membership and record adds, deletes, renames, executable mode or object type changes, and exact content changes. Preserve raw Git path identity. A policy change is itself a control change, and the trusted rule set classifies the entire candidate diff.
- Bind the result and applicable disposition to repository and target, exact base commit/tree, PR and head where applicable, tested commit/tree, trusted and proposed control identities, canonical ordered control diff and exact obligation scope. Scope includes applicable workload/profile, owner/package, runner/platform and policy identities. Keep the authenticated workflow and run/attempt with the proof using that result. Base/head movement or a different control diff or scope requires fresh disposition. A new run attempt needs fresh applicable execution proof.
- `approvals` is the trusted caller's validated input from the existing owner disposition and independent review procedure. The proposed adapter carries sanitized references to both records and their binding. A matching hash, candidate artifact, caller-provided `approved` field from candidate data or `reviewed_tree` alone supplies no authority. Verify exact binding against the trusted input and keep explicit hold reasons for absent, malformed, mismatched, conflicting or superseded records. Establish the caller boundary and the shape of these inputs in the leaf design.
- A detected control change always requires full validation. Until the exact owner disposition and independent review verify, hold even if full execution passed. After they verify, the full requirement still applies. Preserve the fixed #103 coverage floor, required jobs, tests, child proofs, approved skip rules, evidence integrity checks and exact-base outcome comparison. Merge eligibility still requires the existing gate evidence. [Existing outcome comparison](https://github.com/kburson/aitm/blob/56266ed30bbc572b7e56bc64777e802be264c23f/tools/ci/python_gate.py#L282)

### `applicable_inventory(reference, target, dispositions) -> Inventory`

- Start with an independently qualified complete inventory and keep the reference's actual revision, collection and policy identities. Bind the target to the exact scope and revision it represents. The repair route may use an older reference for a broken base. Keep that base, the older reference, and the proposed repair candidate as three explicit identities. Reject local advisory, partial comparison or otherwise unqualified data as an authoritative full reference.
- Consume a verified ordered history from reference to target, including independently established continuity across intervals with no obligation changes. A step binds predecessor and successor commit/tree and policy/scope identities, the expected predecessor and resulting obligation digests, and the exact reviewed row delta where required. Review and delivery evidence must map the step to the actual protected-target revision. Hold on missing steps or coverage, gaps, duplicates, reordered or conflicting steps, drift, and unverified or wrong-scope records. Matching endpoint sets alone cannot establish the intermediate history.
- Apply deltas by the delivered stable obligation key `(provider, owner, platform_scope, nodeid)` and check the full affected rows, including profile, suite, mandatory flag, isolation group, capabilities, child proof and skip constraints. Make addition, removal and semantic changes explicit. Hold on an undeclared removal, deselection, new skip/xfail, weakened obligation, or unreconciled target scope. Preserve existing #103 obligations and require independent evidence for observed outcomes, including full exact-base outcomes for ordinary and selected PR validation.
- Label the result as an applicable comparison inventory derived from the reference and verified dispositions. Preserve the original evidence and carry the derivation and target binding explicitly. Confirm in leaf design how consumers carry that provenance with the accepted `Inventory` return type and delivered v1 bytes.

## Proposed acceptance cases

| Case | Expected result |
| --- | --- |
| `test_control_edit_requires_full_and_independent_disposition` compares a product-only edit and an edit to the workflow, suite policy, verifier, or a discovery control | The product-only edit adds no T10 full trigger. Each control edit requires full and holds without matching independent review and owner disposition. Exact disposition removes that hold and retains full. |
| Move a control across the boundary, remove it, change its mode/type, or edit the file that declares what counts as a control | The trusted rules detect the change from both endpoints and the recorded delta preserves the relevant paths and identities. The candidate cannot redefine the rule for this comparison. |
| Replay a genuine disposition on a different base, head, tested tree, repository, control delta, or platform scope, or submit the same tree string in candidate evidence | Hold. Exact trusted binding is required even if the rest of the evidence is green. |
| `test_reference_inventory_requires_intervening_dispositions` starts from a complete qualified A and walks A → B → C with a scoped addition and an independently approved change permitted under existing policy | The result reconciles the exact C obligation scope, keeps A's actual provenance and identifies the applied history. An independently verified unchanged interval can bridge revisions with no inventory changes. |
| Remove, reverse, duplicate or substitute a step, leave an unverified gap, or provide an A → B → A net-zero change without its history | Hold. Also hold for an advisory or comparison-only reference, the wrong policy or runner scope, a row-digest mismatch, or a missing mandatory, child-proof or capability obligation. |
| Run the comparison with an unexpected skip/xfail, missing required observation, or stale run/attempt in the surrounding proof | Retain the existing hold or failure. Approval and inventory reconciliation do not grant execution evidence. |

At implementation, capture the red/green cases above and run `PYTHONPATH="$PWD/tools/ci" uv run --project packages/aitm-usage --locked pytest -q tools/ci/tests/test_tia_controls.py` from the repository root. Run the related T02/T03 and verifier tests and the applicable exact-head #103 full CI and independent review under the story's delivery authority.

## Size and design questions

**Provisional estimate 3.5 implementation agent-hours.** Allow 0.75h for exact control classification and binding, 0.75h for matching the existing trusted disposition input, 1h for ordered inventory reconciliation, and 1h for focused regression cases and local verification. The estimate assumes one offline module, existing upstream proof inputs and focused tests. External review and hosted queue time are separate.

Before accepting a leaf design, confirm how the existing trusted caller supplies approval, review, delivery and complete ordered history, and how the derived inventory preserves provenance at the consumer boundary. Pinned trunk supplies the Git snapshot, inventory and verifier building blocks. A native owner-disposition feed and authoritative history of scoped inventory transitions are unavailable there. Use fixture-backed consumption for the leaf and hold when real evidence is unavailable. If the design needs a new approval publisher, durable history, hosted integration, a shared schema migration, or more than the parent plan's four-hour limit, refine or split before Develop.

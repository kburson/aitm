## Body and read contract

The body is a generated summary line, a blank line and one fenced `json` block, ending with a newline. Use LF. The object has exactly `schema`, `state` and `run`. The schema literal is `aitm.scheduled-sweep-flag/v1`. Use a strict JSON parser that rejects duplicate keys, extra fields, type coercion and trailing content. Limit the body to 8 KiB of UTF-8. Check that the summary exactly matches recomputed output and disregard comments, labels and other issue fields as evidence.

| Stored state | `run` value | Exact summary template |
| --- | --- | --- |
| `uninitialized` | `null`, only the untouched provisioning body | `Scheduled category full sweep advisory unavailable: no verified result yet.` |
| `active` | Qualifying failure or timeout | `Scheduled category full sweep failed: [run {run_number}, attempt {run_attempt}]({attempt_url}) at {result_at}.` |
| `clear` | Verified successful run | `Scheduled category full sweep flag clear as of {result_at} ([run {run_number}, attempt {run_attempt}]({attempt_url})).` |

A non-null `run` has exactly these fields. `repository_id=1450406435`, `workflow_id=425235652`, positive integer `run_id`, integer `run_number >= 4`, integer `run_attempt=1`, `head_sha` as 40 lowercase hexadecimal characters, `conclusion` and `result_at`. Status `active` pairs with `failure` or `timed_out`; `clear` pairs with `success`. Use a real UTC timestamp in `YYYY-MM-DDTHH:MM:SSZ` form, from the original attempt's `updated_at` per #363. For number 4 accept only run ID `44864075824`, SHA `8ab84ba0590286d4655ea94e4d9de99f25ea1f2e`, and clear. The observed baseline timestamp is `2026-11-21T04:07:11Z`. Above 4 the run ID must differ from the baseline. Derive `attempt_url` from the fixed origin `https://github.com/kburson/aitm/actions/runs/{run_id}/attempts/1`. The exact same `run` is the persisted decision watermark, including while clear. There is no separately writable sequence field.

The #366 JSON check returns the valid record plus a top-level `run_url` equal to the same derived `attempt_url` as the human summary. Human output uses the same parsed fields. For an untouched initial body emit `{"schema":"aitm.scheduled-sweep-flag/v1","state":"unavailable","run":null,"reason":"uninitialized"}`. Use reason `invalid-record` for malformed body or untrusted edit and `store-unavailable` for unreadable, closed or incorrectly bound target. Human output says unavailable for each. An active or clear read succeeds, and unavailable is a distinct unsuccessful read. The timestamp reflects the last verified result and says nothing about an unregistered slot or the publisher's current health.

## Updates and recovery

- Put completion and operator reconciliation in one fixed repository concurrency group (for example `scheduled-category-sweep-advisory`), with no cancellation of an active writer. Enter the group before reading the store or Actions. Put the publisher in a separate trusted `trunk` workflow file, `.github/workflows/scheduled-sweep-flag.yml`. Its workflow ID must differ from `425235652`. Leave `.github/workflows/category-full-sweep.yml` untouched. The publisher runs only trusted `trunk` source and treat both event paths as reconciliation hints. Do not run watched-run code or consume its artifacts in the privileged job.
- Under the group, validate the current body and reconcile authenticated history using #363. Before PATCH, re-read target identity, body and edit metadata and abort on change. Update the summary and JSON in a single body PATCH. Verify by re-reading binding, body, editor and the accepted watermark after the write. An equal or older candidate causes zero writes. Separate job failures report unavailable reconciliation and preserve the valid previous advisory.
- After timeout or an ambiguous write response, re-read first. Matching desired state on the bound issue with correct attribution is success. If the snapshot is unchanged, reauthenticate history and eligibility before a bounded retry. A changed body or competing update stops the attempt. This is a serialized single-writer protocol with readback. GitHub does not document a compare-and-swap on issue body PATCH, so direct human edits can race and are outside the supported write path.
- A missed notification is recovered by the next publisher run or the same authenticated operator reconciliation route. A replaced pending job can therefore be recovered from history. Publisher failures produce visible failed job evidence. Reader timestamps communicate the last verified result if no publisher run has succeeded since.
- A malformed record or edit outside the dedicated App makes the reader report unavailable and stops the writer. A maintainer checks the GitHub issue edit history and Actions result before recovery. Restore a closed issue only after confirming the exact original binding and record. If the body cannot be recovered under the normal contract or the issue is gone, pause the publisher and retain the evidence. Use reviewed re-provisioning with a new immutable issue binding and a recovery floor at least as high as the last defensible persisted watermark. If that watermark cannot be established, wait for a verified new scheduled run registered after the publisher was paused and require that run or a later one as the replacement floor. Resume through the same reconciliation job. The publisher never silently resets or overwrites an unreadable record.

## Target and permissions

During #365, the maintainer provisions one dedicated open issue with title `Scheduled category full sweep advisory` and the canonical uninitialized body. Capture the issue's number, numeric database ID and provisioning author's numeric user ID from the authenticated response and read them back. Pin those three values alongside repository name `kburson/aitm`, repository ID `1450406435` and branch `trunk` in reviewed configuration. Keep the issue out of the story board. On an uncertain creation response, identify the original issue by exact provisioning body and owner in the creation history. Never automatically create another or switch targets.

For every read, query `repository(owner:"kburson",name:"aitm") { databaseId nameWithOwner issue(number:<pinned>) { number databaseId state title body lastEditedAt author { __typename ... on User { databaseId } } editor { __typename ... on Bot { databaseId } } } }` with `gh api graphql` against GitHub.com. Reject GraphQL errors, nulls for required fields, wrong identity/title or a closed or inaccessible issue. A decisive record requires an edit by the pinned Actions bot and non-null `lastEditedAt`. The exact bootstrap record requires the pinned provisioning user as author and null `lastEditedAt` and `editor`. This prevents a human edit from resetting the watermark to the initial marker or substituting a valid-looking decision. The bot identity is shared by Actions workflows, so ownership of other write-capable workflows remains part of the repository's trust boundary.

The trusted publisher job uses its repository `GITHUB_TOKEN` with `actions: read` for run evidence, `checks: read` for job checks/suites, `contents: read` for trusted workflow source and the reviewed sweep blob, and `issues: write` to update the body. Grant permissions at job scope and omit other write permissions. Use only a fixed `PATCH /repos/kburson/aitm/issues/<pinned-number>` request with a JSON `body` field. GitHub grants issue write at repository scope. The pinned identity, fixed route and payload limit the publisher's behavior to this record. An agent needs only a token able to read the issue for authenticated GraphQL. The public browser view requires no write credentials. ## Body and read contract

The body is a generated summary line, a blank line and one fenced `json` block, ending with a newline. Use LF. The object has exactly `schema`, `state` and `run`. The schema literal is `aitm.scheduled-sweep-flag/v1`. Use a strict JSON parser that rejects duplicate keys, extra fields, type coercion and trailing content. Limit the body to 8 KiB of UTF-8. Check that the summary exactly matches recomputed output and disregard comments, labels and other issue fields as evidence.

| Stored state | `run` value | Exact summary template |
| --- | --- | --- |
| `uninitialized` | `null`, only the untouched provisioning body | `Scheduled category full sweep advisory unavailable: no verified result yet.` |
| `active` | Qualifying failure or timeout | `Scheduled category full sweep failed: [run {run_number}, attempt {run_attempt}]({attempt_url}) at {result_at}.` |
| `clear` | Verified successful run | `Scheduled category full sweep flag clear as of {result_at} ([run {run_number}, attempt {run_attempt}]({attempt_url})).` |

A non-null `run` has exactly these fields. `repository_id=1450406435`, `workflow_id=425235652`, positive integer `run_id`, integer `run_number >= 4`, integer `run_attempt=1`, `head_sha` as 40 lowercase hexadecimal characters, `conclusion` and `result_at`. Status `active` pairs with `failure` or `timed_out`; `clear` pairs with `success`. Use a real UTC timestamp in `YYYY-MM-DDTHH:MM:SSZ` form, from the original attempt's `updated_at` per #363. For number 4 accept only run ID `44864075824`, SHA `8ab84ba0590286d4655ea94e4d9de99f25ea1f2e`, and clear. The observed baseline timestamp is `2026-11-21T04:07:11Z`. Above 4 the run ID must differ from the baseline. Derive `attempt_url` from the fixed origin `https://github.com/kburson/aitm/actions/runs/{run_id}/attempts/1`. The exact same `run` is the persisted decision watermark, including while clear. There is no separately writable sequence field.

The #366 JSON check returns the valid record plus a derived top-level `run_url`. Human output uses the same parsed fields. For an untouched initial body emit `{"schema":"aitm.scheduled-sweep-flag/v1","state":"unavailable","run":null,"reason":"uninitialized"}`. Use reason `invalid-record` for malformed body or untrusted edit and `store-unavailable` for unreadable, closed or incorrectly bound target. Human output says unavailable for each. An active or clear read succeeds, and unavailable is a distinct unsuccessful read. The timestamp reflects the last verified result and says nothing about an unregistered slot or the publisher's current health.

## Updates and recovery

- Put completion and operator reconciliation in one fixed repository concurrency group (for example `scheduled-category-sweep-advisory`), with no cancellation of an active writer. Enter the group before reading the store or Actions. Keep the privileged publisher outside the watched sweep, execute only trusted `trunk` source and treat both event paths as reconciliation hints. Do not run watched-run code or consume its artifacts in the privileged job.
- Under the group, validate the current body and reconcile authenticated history using #363. Before PATCH, re-read target identity, body and edit metadata and abort on change. Update the summary and JSON in a single body PATCH. Verify by re-reading binding, body, editor and the accepted watermark after the write. An equal or older candidate causes zero writes. Separate job failures report unavailable reconciliation and preserve the valid previous advisory.
- After timeout or an ambiguous write response, re-read first. Matching desired state on the bound issue with correct attribution is success. If the snapshot is unchanged, reauthenticate history and eligibility before a bounded retry. A changed body or competing update stops the attempt. This is a serialized single-writer protocol with readback. GitHub does not document a compare-and-swap on issue body PATCH, so direct human edits can race and are outside the supported write path.
- A missed notification is recovered by the next publisher run or the same authenticated operator reconciliation route. A replaced pending job can therefore be recovered from history. Publisher failures produce visible failed job evidence. Reader timestamps communicate the last verified result if no publisher run has succeeded since.
- A malformed record or non-bot edit makes the reader report unavailable and stops the writer. A maintainer checks the GitHub issue edit history and Actions result before recovery. Restore a closed issue only after confirming the exact original binding and record. If the body cannot be recovered under the normal contract or the issue is gone, pause the publisher and retain the evidence. Use reviewed re-provisioning with a new immutable issue binding and a recovery floor at least as high as the last defensible persisted watermark. If that watermark cannot be established, wait for a verified new scheduled run registered after the publisher was paused and require that run or a later one as the replacement floor. Resume through the same reconciliation job. The publisher never silently resets or overwrites an unreadable record.

The #365 JIT join uses #363's inclusive floor, original attempt rule, run-number comparison and exact timestamp. This receipt defines how those values are stored together and how humans and agents read them. Provisioning, token write validation and replay are implementation work for #365.

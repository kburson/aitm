## Typed API and exact storage selection

- Add one trailing optional `dispute` field to existing `JournalChange`, with `_JournalDispute` as a frozen wrapper of exactly one typed `OwnershipDispute | ContentDispute`, canonical storage identity, original project UUID and row digest. The ownership digest is the stored lowercase hexadecimal `d.digest`; the content digest is SHA-256 of the exact canonical `d.payload`. Canonical storage identity is the existing service-evidence keyed reference to the full typed row identity, not an editable free string. For ownership include key, contender, original project, digest, exact canonical evidence and sequence. For content include key, original project, exact canonical content digest and sequence. Existing constructors and `JournalView` layout are preserved. Reject combinations of dispute with coverage, disposition or paired. Existing disposition+paired behavior is unchanged. Define a frozen `PublicationCandidate` with journal sequence, an exclusive private basis (coverage or dispute), and a service-authenticated candidate identity. It contains no provider transcript, usage payload, quota, project receipt or ACK. Candidate fields can be reread and reverified by a later recovery consumer. No consumer is wired by #310.
- Add `RoutingJournal.dispute_changes(after_sequence)` so callers can get exact durable typed changes from both existing dispute tables. Read existing schemas before queries. For ownership use `SELECT d.key,d.contender,c.project,d.digest,d.evidence,d.sequence FROM disputes d JOIN claims c ON c.key=d.key` with bounded sequence and optional exact claim key, order by sequence, native key, contender, digest and evidence. Validate the source key, project/contender UUID and 64-character lower-hex `d.digest`; decode `d.evidence` with the existing service key validator, re-encode and compare exact bytes. Verify the original stored claim row before treating `c.project` as durable destination custody. For content use the existing `as_of` join to claims and `_stored_content_dispute` to authenticate original span, row integrity and service references. Factor the existing ownership/content decoding or row queries only where it preserves `as_of` outputs and order exactly. The new read method produces exclusive `JournalChange` values with one wrapper per canonical stored row. Two valid disputes may share one sequence and are distinguished by their whole row identity, even if they refer to one key.
- `RoutingJournal.publication_candidate(change)` validates type and exact positive sequence within current journal tip and reads under one existing private read transaction. For coverage require v6 or later recognized schema, query `_COVERAGE_ROWS` at this exact sequence, and use `_stored_coverage` to verify row presence, identity, seal, full canonical bytes and bound sequence. A forged, mixed, altered, below-schema, foreign or future change is refused. For dispute restrict readback to exact sequence and claim key, compute checked wrappers from stored rows, and require exactly one canonical typed match. Compare the reconstructed type, stored fields, digest and keyed identity, and reject ambiguity/corrupt rows even on retry. No equality-only authorization for unvalidated incoming fields. Existing ordinary disposition/paired types alone never issue journal-only candidates.
- Use current `self._store.evidence.pseudonymize` and `validate_source_ref` with new namespaces for dispute row identity and candidate identity. These are deterministic non-persisted HMAC references. Candidate identity binds the canonical verified change and basis under the existing journal key, so restart and duplicate attempts return the same value while different rows at the same sequence do not. No new key, write, schema bump, journal sequence, public publication, destination open or ACK. Keep checked type definitions in `monitor_journal.py` and focused regression cases in existing test files.

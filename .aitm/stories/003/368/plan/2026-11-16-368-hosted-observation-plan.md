# #368 hosted macOS observation qualification plan

## Experiment question

Can the GitHub-hosted macOS runner family used in #146 protect an independent controller and produce trustworthy observations for exactly #354's 30 pinned obligations? This owner-approved revision changes the execution location for the next #368 experiment. The [accepted local plan](2026-11-16-368-protected-local-observation-plan.md) remains the authority for the completed local attempt and for the unchanged assignment, observation and refusal criteria carried into this plan.

Both experiments answer different parts of the question. The offline local guest verified the practical pre-commit isolation conditions and exercised the worker's scratch-write and protected-path controls. Its stock DTrace then refused the required process probe, so there was no local assignment execution. The fresh hosted experiment checks whether #146's previously observed process and user-space tracing can support this precise assignment under a new protected boundary. Publish both results and why each was needed. A hosted pass establishes a bounded hosted configuration. Local execution and resistance to unreviewed in-process code remain unqualified. ## Stage A · Qualify the hosted runner boundary and trace capability

1. Run a qualification-only workflow mode before any product pytest. The owner authorized the hosted experiment. Its privilege scope is the standard GitHub job account and its documented sudo for creating a distinct unprivileged guest worker, establishing protected directories, and running stock DTrace from the controller. Capture role, worker groups, sudo denial, exact image/OS/architecture, APFS, SIP and tracing provider readbacks. A required protection change or unavailable capability produces HOLD. Run only on the trusted workflow commit and turn checkout credential persistence off.
2. The hosted controller may use GitHub and published dependency sources for staging and evidence transport. During every worker launch, use #146's separate UID, scrubbed environment with no credential or agent variables, and an enforced worker sandbox. Require read access to the manifest of staged/runtime inputs and needed system files, scratch-only writes and network denial. The worker must have no access to checkout, controller home, host shares, protected control paths, token fixtures or evidence stores. The controller stages pinned tools and dependencies before worker execution. Use guest-local synthetic markers for each protected path, including credential canaries that contain no secrets. Record permitted input reads and scratch writes, denied reads/writes and mode/owner/digest readback. Prove an out-of-scratch write is refused even against a worker-writable synthetic sentinel, and show the worker cannot open or connect a socket to a controller-created local test listener. Verify the controller's positive listener observation and matching worker denial without any external network traffic. Appended media and stdout from the worker carry no verdict authority.
3. Use the normal product worker-launch path for a benign pinned probe only. In a fresh invocation, observe actual OS create, exec, and exit and the direct wait result from outside the worker. Observe a pinned benign USDT event through the controller. Protected logs, attempt identity and trace health must agree. Refuse on missing provider, absent rows, drops or ambiguous identity. Review the exact workflow and probe code and its static input hashes before pushing this admission-only job. A failed admission job yields a bounded hosted HOLD and a paired findings report. After this gate passes, build the instrumented CPython and patched pytest in Stage A using the reviewed commands, pinned public sources, patches and the #368 product lock on the same hosted image. Use a stable private runtime prefix so the next job can import the same bytes at the same prefix. Keep build log, runner/toolchain identities and a per-file mode and SHA-256 manifest, record the interpreter and installed pytest digests and Mach-O probe table digest, and verify that no product runtime path embeds Stage A-only inputs. Export only the reviewed public runtime bundle and its manifest. Download and retain it before any rerun, verify its archive and manifest through authenticated run, attempt and artifact identity, then bind them in the Stage B packet. Build failure, missing provenance or a live admission HOLD stops Stage B.

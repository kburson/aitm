## Independent verdict

CHANGES_REQUIRED

The corrupt-index rebuild can attach the previous WAL to the replacement database and mix trees. `index_snapshot` recovers by building a WAL database in a temp directory and `os.replace`s only `index.sqlite`. SQLite keeps the snapshot in `-wal`/`-shm` beside the path. The old sidecars are not removed, and the new ones are not moved. A later open replays the old WAL onto the new file.

Repro: build a WAL index for tree A and leave `index.sqlite-wal` in place (open reader, or a crash before checkpoint). Overwrite `index.sqlite` with non-database bytes. Call `index_snapshot` for tree B. Open that path again. The connection sees B’s main file plus A’s WAL, so it raises `SQLITE_CORRUPT` or returns rows from A while `metadata.tree` says B. That breaks the atomic single-tree swap.

The rest of the packet holds. A normal rebuild commits in one `BEGIN IMMEDIATE`, and a read transaction stays on the tree it pinned. A missing, stale, or busy index falls back to an in-memory build of that same snapshot. FTS covers titles, description text, idea bodies, draft bodies, and lessons. `show`, `list`, `search`, `explain`, and `discuss` report the pinned commit, tree, and code/shared freshness. Cached reads do not fetch or publish. `--refresh` uses C08. `discuss` only returns the packet and a suggested command. With no explainer, `explain` is `unavailable`, drops the rows, and does not treat the query view as a guard explanation.

The coordinator reproduced replacement of a damaged database path with a live WAL sidecar present. The PR returned to draft for recovery that publishes a new isolated SQLite path and switches only the locator.

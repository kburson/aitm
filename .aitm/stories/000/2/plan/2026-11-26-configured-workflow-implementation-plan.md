# Core #2 Configured Workflow Implementation Plan

> **For agentic workers:** Use subagent-driven-development or executing-plans for an authorized child. Each child's Design, Plan, JIT applicability, and delivery rules still govern pickup.

**Goal:** Deliver Core in bounded, independently mergeable mini-epics and replace the fixed lifecycle with the accepted configured workflow.

**Architecture:** Core loads an ordered graph and binds versioned capabilities to typed guards, directives, and actions. The existing planning store and dispatch authority own durable transitions, evidence, and host effects. Hosted providers, TIA, and agent cost capture have separately delivered interfaces.

**Tech stack:** Python 3.13, committed TOML, Git plumbing, the Core typed services and existing CLI, installed Python extension entry points, and the existing GitHub and harness adapters.

**Spec:** [Accepted configured workflow amendment](../design/2026-11-26-configured-workflow-amendment-draft.md), finalized in [XPR publication 07755fa0](https://github.com/kburson/aitm/commit/07755fa0bf8e5fabdcadbce0eb31a126b5cc6303). **Status:** Proposed implementation-plan revision for review. The design amendment is accepted. This decomposition and its estimates remain proposals until reviewed and reconciled. The prior [accepted baseline plan](core-implementation-plan.md), [leaf ledger](leaf-stories.md), and [governed PR plan](2026-11-11-2-governed-pr-and-branch-lifecycle.md) retain their reviewed bytes and remain the source for inherited child contracts. ## Delivery and sequencing

- Use #2 as the Core coordination record. The proposed mini-epics are sibling delivery epics under product #1, linked from #2 by the ledger. #2 has no collective implementation branch or final integration PR. Preserve #2's downstream #247 dependency until its readiness contract is reconciled with the released capability it consumes.
- Each Core mini-epic has four to six direct children, including one designated integration owner. A child includes implementation, verification, and source review within four estimated agent-hours. Integration adds 0.5 h to bounded owners where it fits. For substantive new owners C94, C95, C96, and C101 the cap comprises **3.5 h for the named contract and its tests/review + 0.5 h for exact slice proof and trunk integration**. Use the existing resource/dispatch paths. For C110 the split is **3 h + 0.5 h**. Three narrowly scoped integration leaves cover slices whose final owners were already at four hours. If actual scope does not fit at JIT, split and rebalance before pickup.
- Open one working integration branch from current trunk and one upstream draft PR per mini-epic at authorized pickup. While Core is being built, use the existing authorized PR workflow to do this. Children branch from the integration ref and deliver their own reviewed PRs there. Their delivery documents remain on planning. The designated child's final integration work consumes exact child deliveries, verifies the composed delta and its own changes, and lands the mini-epic on trunk under the repository's current CI, review, and merge controls. Record the ledger's required sibling-delivery set in the accepted epic decomposition and admission fixture. The integration owner may prepare the shared resource in Plan before those siblings deliver. Its merge authority requires the exact verified deliveries of every listed sibling, the declared slice proof, and only the listed prerequisite trunk receipts.
- An earlier slice can merge code, tests, or a disabled capability before the complete Core CLI is usable. Each merge must pass its own affected checks and trunk regressions. Leave unfinished routes unavailable through normal capability and feature checks. Public release, production migration, and repository policy changes retain their separate authority. Each slice uses the normal CI and review route.
- Release preparation and the read-only observer land with the packaging mini-epic. #72 then qualifies the exact separately authorized release. #72 is a child of that mini-epic and needs the earlier source merge. It does not block landing the source it must subsequently qualify.
- M2 GitHub and M3 harness retain real provider and runtime proofs. Core can land its typed ports and broker-fixture behavior first. A merged fixture path does not enable managed production routes. Preserve the #158 hosted default-target boundary, #159 prerequisites, existing C5 release and C6 cutover gates, and all currently accepted leaf dependencies unless a specific reviewed revision changes them.
- TIA and Agent Cost Capture have separate packaging tracks and independent versions. Core consumes fixture contracts and runs without these packages. The existing #228 and #229 timing follow-ups remain after #72. #230 remains the live Cost qualification outside M1, with #51 and #459 retained as dependencies.

## Summary

Cross-provider (XPR) review of the full current `core-design.md` (614 lines, raw digest `sha256:f791fdf0…efaac1`, the SPR-accepted bytes), read against the parent `../../1/design/architecture.md` (lifecycle, enforcement modes, review contract, providers, Done dispositions) and the SAR/SPR manifests to avoid re-litigating settled items. I did not re-open the owner questions the document correctly leaves open (expansion-completion interpretation, second-trip cap, review-depth matrix, GitHub every-push audit, distribution name).

The design is unusually rigorous on integrity, idempotency, evidence retention and conflict semantics, and it reconciles the architecture's listed obligations (single-owner persistence, canonical authored-content acceptance, M1 review import, authoritative configuration, delivery-before-Done, evidence recovery). The SAR and SPR rounds closed many correctness holes. What this pass found is mostly a different class of problem: places where the document's own acceptance bar cannot be met by `aitm-core` alone as specified, a few mechanisms that are left undefined although the nominal walk depends on them, one deliberately strict rule whose safety benefit is already supplied by another mechanism in the design, and several builder-facing ambiguities (terminal model, publication default, bootstrap ordering, store topology, read budget versus policy refresh). None requires an owner decision; each is resolvable at the builder-design level.

## Findings

1. **Time-limit trip cannot be demonstrated by `aitm-core` alone (Goals 5, Trip/Timing acceptance).** Goal 5 requires enforcing the trip rule, and the Acceptance preamble says the core is complete only when "a temporary repository with `aitm-core` alone demonstrates the nominal walk and failure cases below", including "supported observed engagement exceeding the limit does prove one" (Timing and outcomes row) and "observed engaged-time overrun" (Trip and attempt row). But the design also says only intervals from "a producer [that] actually observes that actor's active reasoning/interaction … with a supported measurement contract" count; that "Core-only observations may be unable to establish any nonzero engagement lower bound"; that CLI-gap estimates and tool durations are never proof; and the event table lists the eligible producer of `core.activity.recorded` as "later harness extension" (line 260). No core-shipped producer satisfies the measurement contract, so the time-limit trip can never be *confirmed* in a core-only install, and the acceptance case can only be met with an unspecified test double. The design needs to say which of these is intended: (a) core defines the producer contract and registration point (e.g., an `ActivityProducer` registration in the extension API with declared measurement contract/coverage class) and its acceptance proves confirmation with a contract-conforming fixture producer, while a core-only install reports only "possible overrun / coverage missing"; or (b) core ships a qualifying producer. As written, Goal 5 is overstated for time limits and the acceptance row is unverifiable. (Expansion-count trips are unaffected; they are fully observable by core.)

2. **The authoritative test execution lane is required but never specified (Verification; nominal walk).** `test` may issue an authoritative pass only from "a captured stable input snapshot, or an execution lane with equivalent evidence"; "Merely comparing hashes before and after execution is insufficient"; a lane that cannot establish stable inputs is diagnostic only. The nominal core-only walk requires an authoritative pass ("run the configured test over the recorded clean input"), yet the design never states what M1's lane is. Builder-relevant constraints interact here and are unaddressed: the `bind` section says the core "never … creates/removes a worktree"; the default `[test] command = "uv run pytest"` resolves a project environment relative to the working directory, so running from an exported snapshot directory may create a fresh venv and touch the network (contradicting the separately reported local budget and the offline/core-only story); and making "declared source/fixture inputs immutable for the run" needs a concrete mechanism (read-only export via `git archive`/`checkout-index` into a private temp dir plus copied accounted untracked inputs, or similar). Without a named M1 lane and its environment rule (where the venv/cache lives, whether network is permitted, how generated outputs are separated), two builders would implement incompatible things and the nominal walk's central evidence step has no defined implementation.

3. **Pre-dispatch shared-ref admission for side-effect-free local tests duplicates protection that publication replay already gives (Managed start and dispatch admission).** The design requires that in any store with a shared planning ref "every authoritative managed start, including a local test, must have its admission verified in that shared order before dispatch", with no offline fallback. For external, non-idempotent side effects (issue creation, target mutation) this pessimistic rule is necessary. For a local test run it is not: the same document already guarantees (i) replay at publication reapplies "only whole local operations whose complete read/write-set and policy preconditions still hold on the new published prefix", (ii) a published stop changes those preconditions, and (iii) "Already produced unadmitted output … cannot be promoted into an authoritative execution receipt merely by publishing it later." An optimistic local admission (durable local CAS, launch, retain result) followed by publication therefore cannot let a post-stop offline run become authoritative: its admission fails replay and the receipt is retained as stale/diagnostic evidence — the identical outcome the current rule achieves by not launching. The current rule's costs are real: every authoritative test in a shared store needs network plus at least one push before launch (and another after), creating push contention across the eight parallel stories the acceptance targets, and an offline developer in a shared store can never produce an authoritative receipt even though the result would be validated on reconnect anyway. The safety property the design wants ("Core guarantees the ordering of admissions and stops") is preserved by ordering at publication. Either adopt optimistic admission for side-effect-free managed verification (keeping pessimistic shared admission for external/target side effects), or state the specific property the pre-dispatch rule protects that replay-time validation does not.

4. **The terminal/disposition model is not defined, and the CLI and event table don't cover it (State machine; Events; CLI).** The architecture defines Done with dispositions delivered, abandoned, superseded, duplicate. The design uses `done/delivered` and introduces `done/unverified` (an advisory-only terminal not in the architecture's list) and refers to "an explicit abandon/supersede/duplicate disposition", yet: (a) there is no disposition enum or statement of whether `unverified` is a Done disposition or a qualifier on `delivered`; (b) `core.state.changed` data is `from, to, reason, mode` with no disposition or replacement-story field, and no other event in the table carries a terminal disposition (`core.signoff.recorded` carries a verdict, not the state change); (c) the CLI lifecycle group has `abandon --reason` but no supersede/duplicate command, although dependency resolution requires "duplicate/superseded also follows a valid replacement without cycles", i.e., a replacement reference must be recorded somewhere; (d) the "Recorded by" column for `core.state.changed` lists only `promote, demote, abandon`, while `signoff`, `reopen`, `trip`/rules engine, `pivot` and expansion/trip demotion also change state; and (e) it is not stated whether `signoff` itself performs Review→Done or whether a subsequent `promote` is required (the Review exit guard lists `signed-off`, implying sign-off precedes the transition, while the `signoff` paragraph says it records "Done disposition"). The eight-state count in `machine/states.py` is right per the architecture only if dispositions are data on Done; the design should say so and define the payload.

5. **Fresh bootstrap publishes and protects the planning branch before the trust anchor lands, which can strand an undeletable orphan (init steps 3–5; Fresh bootstrap sequence; Trust anchor).** Step 3 publishes the new planning branch "when a remote is configured", and step 4 immediately protects it with no deletion and no bypass actors, while step 5 leaves `.aitm.toml` (carrying the expected UUID/genesis) uncommitted for the user's PR. If that PR is rejected, edited (e.g., a reviewer changes the branch name or policy), or the initiating clone's local bootstrap journal is lost, step 2 refuses any other clone's `init` because the existing branch matches neither "the configured trusted anchor" (not yet committed) nor that clone's journal — and protection forbids deleting it without an admin disabling the rule. No recovery path for an abandoned bootstrap is specified. Since no routine writer may run while bootstrap is pending anyway, and a fresh clone only needs the planning branch after the config lands, publication and protection could be deferred to the post-landing `init` rerun (which already "verifies policy, store and publication"), eliminating the stranded state; alternatively, specify an explicit abandoned-bootstrap route with the exact owner action required.

6. **The 150 ms read budget conflicts with the policy-refresh rule for `explain`, and Python start-up cost is not addressed (Performance; Configuration).** The configuration section says "Before a command evaluates policy, the core attempts to refresh the configured default and planning refs", records fetch status, and treats freshness-dependent guards as not passing when stale. `explain` evaluates each guard's pass/fail/unknown against "the pinned state/policy", so under that rule it fetches from the remote, which cannot fit "under 150 ms" even with a warm index. The budget's qualifier ("warm index matching the pinned validated local tree") implies no fetch, but the design never states that read-only commands skip refresh (and how they then report freshness). Separately, with the specified stack (Python 3.13, Typer, Pydantic v2 models for every event type, SQLite), interpreter start plus eager imports of the CLI tree and all event models commonly consumes most of a 150 ms budget before any work; extension entry-point discovery adds more. A builder needs the rule (read commands use the last validated local refs and display freshness; `--refresh` opts in) and an explicit lazy-import/lazy-extension-load constraint, or the budget should be stated as excluding interpreter start.

7. **The shared local-numbered allocation authority is redundant with "publish before exposing the ID" (Local backlog provider; Migration).** The design already requires that in a shared store "final allocation/initialization must be accepted at the shared planning ref … before the permanent ID is exposed as issued", and the planning ref is fast-forward-only with CAS replay that re-checks preconditions. Under those two rules any clone can safely allocate: it proposes the next number locally, pushes; if another clone published that number first, the push is rejected, replay finds the allocation precondition false, and it re-allocates — the ID was never exposed, so nothing was issued twice. The additional single "allocation authority" with generations, handoff, takeover fencing, "route graduation to that authority or wait", and the authority holder recorded in `store.json` and the migration declaration adds a distributed-ownership protocol (and an unspecified routing mechanism — there is no service through which another clone could "route graduation to that authority") without adding a safety property I can identify. If the authority exists for a reason not stated (e.g., a provider without monotonic numbering, or a desire for gap-free numbers), the design should state it; otherwise removing it simplifies `store.json`, the adoption declaration, and the migration acceptance row.

8. **Default publication behavior of state-changing commands is unspecified (Planning backend; CLI).** The CLI has `sync [--push]`, the result contract distinguishes "locally-committed" from a "requested remote completion that is pending", and many rules depend on publication (shared admission, shared projections, graduation intent, dispatch claims). But the document never says whether `promote`, `test`, `describe`, `review import`, etc. publish automatically when a remote is configured, publish only with a flag, or publish only via `sync --push`. This determines user-visible latency, the nonzero-exit semantics ("A requested remote completion that is pending returns a distinct retryable nonzero result"), and contention behavior. One sentence fixing the default (and which commands always require publication because they need shared ordering) is needed.

9. **"Story-tagged implementation commits" has no defined tag (Develop exit guard).** The Develop exit guard requires the recorded attempt branch to contain "story-tagged implementation commits", and the walk requires "a real story-tagged change", but the tagging convention (message prefix such as the repository's existing `[#2]`, a `Story:`/`aitm-story:` trailer, or both) and its parsing rule are not specified and are not listed under "Left to the builder". Because this guard reads code facts captured in preflight and must be deterministic across clones and providers (squash/rebase may rewrite messages), the tag form and how it survives provider transformations should be stated.

10. **Store topology language exceeds what configuration can express (Guarding the planning branch; Configuration; Local index).** The ref/worktree boundary refers to "the actual store Git common directory", "including when code and store locations differ", and "A bare dedicated store naturally has no checkout". The configuration has only `[store] remote` (a remote name) and `branch`; per the architecture, moving planning to its own repository is "a config change" of the remote. In that model the planning ref still lives in the code clone's object database and common directory, so there is no separate store common directory or bare store to enumerate, and the index location `<git-common-dir>/aitm/index.sqlite` is unambiguous. If a separate local store repository is intended, configuration needs a store-path setting and the index/lock locations must say which common dir they use; if not, the "bare dedicated store"/different-location wording should be removed to avoid a builder implementing an unconfigurable mode.

## Required changes

1. Resolve finding 1: state how the time-limit trip is confirmed in a core-only install. Either (a) define a core activity-producer registration/measurement contract, state that core-only installs report possible overrun/missing coverage rather than confirmed time trips, and change the Timing/Trip acceptance rows to prove confirmation with a contract-conforming fixture producer through that registration; or (b) specify the core-shipped qualifying producer. Adjust Goal 5's wording accordingly.
2. Resolve finding 2: specify the M1 authoritative test lane — how the recorded tree and accounted untracked inputs are materialized read-only (without contradicting the "never creates/removes a worktree" rule, or amend that rule), where generated outputs and the tool environment/venv live, whether the lane may use the network, and how the default `uv run pytest` command behaves in it.
3. Resolve finding 3: either restrict pre-dispatch shared-ref admission to managed actions with external or target side effects and allow optimistic local admission for side-effect-free managed verification (validated at publication replay, failing replay yielding retained stale/diagnostic evidence), updating the Trip-and-attempt acceptance row; or state the concrete property the current rule protects that replay-time validation does not.
4. Resolve finding 4: define the Done disposition enum (including whether `unverified` is a disposition and how it relates to the architecture's four), the event field(s) that carry disposition and replacement reference, the CLI route(s) for supersede/duplicate, whether `signoff` performs Review→Done, and the complete "Recorded by" list for `core.state.changed`.
5. Resolve finding 5: either defer planning-branch publication and host protection until the bootstrap config has landed on the anchored default branch (performed by the verifying `init` rerun), or specify the abandoned-bootstrap recovery route and the exact owner action needed when a published, protected, never-anchored branch exists.
6. Resolve finding 6: state whether read-only commands (`show`, `list`, `search`, `explain`) refresh refs; if not, how they report freshness and how a user requests a refresh. Add a lazy-import/lazy-extension-loading constraint or state that the 150 ms budget excludes interpreter start-up.
7. Resolve finding 7: remove the shared allocation authority in favor of publish-before-exposure allocation with CAS replay, or state the property it adds and specify the actual routing mechanism by which a non-authority clone hands graduation to the authority.
8. Resolve finding 8: state the default publication behavior for state-changing commands when a remote is configured, and which commands always require shared publication.
9. Resolve finding 9: define the story-tag convention for implementation commits and how the guard evaluates it after provider squash/rebase, or list it explicitly under "Left to the builder" with the determinism constraint.
10. Resolve finding 10: either add a store-repository location setting and specify which common directory the lock, index and worktree enumeration use, or remove the separate-store/bare-store wording so the topology matches `[store] remote` + `branch`.

## Optional suggestions

1. Add a short "Build order" section mapping mechanisms to the minimum slice each acceptance row needs (e.g., local-only single clone: store, events/fold, GitBackend CAS, index, guards, describe/review import/accept, test lane, deliver/signoff; then shared-store publication/replay, continuity journal, repair, dispatch claims, migration). It would not remove any requirement, but the Intent says the core must be "small enough to learn Python from", and the current document presents roughly forty interlocking mechanisms with no ordering, which makes planning hard and invites a big-bang implementation.
2. Extend the `.aitm.toml` example (or add a second, bootstrap-complete example) showing the key names for the expected store UUID, planning repository/ref, genesis commit, review-policy ID/schema/levels, and legacy-anchor declaration. The text says these are mandatory committed configuration but never names them, so the builder must invent the schema the trust model depends on.
3. Many paragraphs (e.g., Published continuity, Forward repair, Managed start and dispatch admission, Expansion transaction) pack ten or more normative constraints into one block. Converting the normative clauses of those paragraphs into numbered rules would make each one individually citable from tests and plan tasks without changing content.
4. A refused workflow operation commits its guard records to planning. Consider noting the expected volume (e.g., an agent retrying `promote`) and whether repeated identical refusals against the same pinned inputs are deduplicated, since in a shared store each refusal is also a publication.
